## 1. 第 1 项：冲突可见性矛盾（评审指出的核心缺陷）

### 1.1 评审的观察是正确的

评审指出：

> `docs/sync-protocol.md` 声明"同一对象的并发修改必须可见，要么合并，要么产生冲突记录"。
> 但在合并策略表中，`lww` 对任务状态、日期、时刻、分类和单值关系采用确定性胜者，
> 落败值仅保留在操作日志中，并不一定出现在用户可见的冲突列表中。这两项设计不一致。

**确认成立，且比评审描述的更严重。** 我在修复时发现：

`lww` 字段丢弃落败写入时，**落败写入的版本向量从未被合并进 `field_register`**。
后果有两层：
1. 落败 op 在之后每次同步时都被重新评估、重新丢弃；
2. 更严重：一旦第三台设备的写入到达，被丢弃的值**在原理上都无法再恢复**，
   因为寄存器已不知道"曾观察到这个落败版本"。

也就是说，这不只是"用户看不到"，而是"数据真的没法找回来了"。

### 1.2 修复后的规则

**触发条件（必须同时满足）**：
1. 两个写入是**真并发**的（版本向量互不支配）；
2. 两边的**值不同**。

**明确不触发**：因果更晚的写入；并发但值相同；顺序编辑。

这条限定很关键——没有它，正常编辑会淹没在冲突提示里，
用户就会开始忽略提示，真正的冲突反而被漏掉（风险 CC-3）。

- **所有策略**（`lww`/`text`/`set`）在触发时都写入 `conflict` 表；
  `strategy` 只决定呈现方式（文本多存一份正文）。
- 冲突记录 `conflict_id = hash(losing_op, winning_op, field)`：确定性、可去重、跨设备一致。
- **冲突行本身不同步**，由两端各自从 `op` 推导 → 不存在"冲突表同步"这一额外协议。
- 解决 = 写一条普通 `set` op → 复用已测试的版本向量与总序机制，天然可同步可收敛。

### 1.3 新增的 13 条原型测试（全部通过）

```
21 review: concurrent scalar (lww) writes produce a VISIBLE, open conflict
22 review: conflicting value is recoverable and both sides agree on the loser
23 review: a causally-later write produces NO conflict
24 review: concurrent writes with the SAME value produce NO conflict
25 review: ordinary sequential editing never creates a conflict
26 review: re-delivering the same ops does not duplicate conflict records
27 review: conflict set converges regardless of the order devices pull in
28 review: choosing the losing value resolves and converges on all devices
29 review: resolving the same conflict twice is rejected as already resolved
30 review: resolving cannot resurrect a value without a new op (auditability)
31 review: a discarded losing write still merges its version vector
32 review: concurrent set-membership removal vs add still converges to union rules
33 review: text conflicts remain visible and resolvable end to end
```

覆盖了评审要求的全部方面：多设备（21/27）、不同同步顺序（27，6 种交错）、
重复投递（26）、冲突解决后的收敛（28）。

**测试总数：20 → 33，全部通过（`cd prototype/sync-core && node test/run.js`）。**

### 1.4 修复过程中发现并修复的另外 5 个真实缺陷

这是本轮最有价值的部分——**把承诺写成可执行测试，暴露了文档评审看不到的问题**：

| # | 缺陷 | 后果 | 修正 |
| --- | --- | --- | --- |
| 4 | `orderOps` 最终并列判据读 `op.op_id`，而字段寄存器用 `opId` | 寄存器与 op 比较时该判据**静默失效**，总序失去最后一级确定性 | 统一 `opIdOf(x)` |
| 5 | `snapshot()` 只读 `opId` | 对传入 op 取快照时 `opId` 恒为 `undefined`，JSON 又丢掉 undefined 字段 → 冲突记录**丢失 `losing_op`**，既无法解决也无法收敛 | `snapshot` 同时接受两种命名；缺失 op id 直接抛错 |
| 6 | 落败写入未合并版本向量 | 见 §1.1，数据不可恢复 | 无条件合并 |
| 7 | `observeRemoteClock` 只在 `pull()` 内 | 其他 apply 路径（重试/重放）在未推进 HLC 时应用 op → **错误排序与虚假冲突** | 观测移入 `applyOp` |
| 8 | 冲突在创建同一毫秒被自动关闭 | 用"支配落败向量"作自动关闭判据，获胜方自己应用写入就关掉了冲突，用户永远看不到 | 自动关闭还要求当前 op 既非落败也非获胜 |

> 缺陷 8 特别说明"为什么必须写成测试"：它是我第一次修复尝试**自己引入的 bug**，
> 只有跑测试才发现冲突刚创建就被关闭。

### 1.5 一个刻意的行为（需要用户知晓）

用户选择 `keep_winner`（保留已经是当前值的那一版）时，字段值不变，
因此**其他设备上该冲突仍显示为待处理**。

这是有意为之：其他设备仍需要知道"这里发生过并发编辑"。
`keep_loser` 会发出新写入，因此在所有设备上都会关闭。

若认为不合适，正确做法是**显式同步一条解决记录**（建议 S1），
而不是放松"必须产生新写入"的判据。已列为待决问题 **Q9d**。

## 2. 第 6 项：中文搜索实测（本轮意外收获）

评审要求"使用至少 5 万条混合中英文测试记录"比较方案。**我实际执行了**——
本机 Node 26 内置 SQLite 3.53.3 且**编译了 FTS5（含 trigram）**，
因此不需要等 Flutter 工具链就能做真实基准。

### 2.1 关键实测结果（20 万条）

| 方案 | 平均召回 | 3 字中文查询 | 2 字中文查询 | 索引体积 |
| --- | --- | --- | --- | --- |
| `unicode61`（FTS5 默认） | **13.2%** | **0% 召回** | **0% 召回** | 1.31× |
| **`trigram` + `LIKE` 回退** | **100%** | **0.09 ms** | 34.1 ms | 2.72× |
| 自研 `bigram` | 100% | 0.82 ms | 0.94 ms | 4.98× |
| 纯 `LIKE` | 100% | 32.9 ms | 34.0 ms | 1.00× |

### 2.2 结论

**推荐 `trigram` + 短查询 `LIKE` 回退**：
- 全长度 100% 召回、100% 精确；
- 3 字以上比 `LIKE` 快 **350–800 倍**；
- 1–2 字回退 `LIKE`，延迟与纯 `LIKE` 相同（桌面 20 万条 34 ms，可接受）；
- 无需自研切分逻辑（`bigram` 需要，且索引体积近 5×）。

**必须明确的两点**（避免"提前宣称可用"）：
1. **FTS5 默认分词器中文召回率 0%**，任何"用默认配置做中文搜索"的方案都是无效的。
2. 上述延迟是**桌面 Windows** 测量值。Android 预计慢 2–5 倍，
   **移动端实测通过前不得宣称"中文搜索已可用"**。

### 2.3 我的第一版基准本身有缺陷，已修正

第一版统计把 **13 条零真值查询**按"召回=1"计入，虚高了召回率。
修正后：零真值查询单独计数并从召回分母排除，同时输出"最差召回案例"与语料自检信息。
这类方法论错误如果不修，基准会给出好看的假数字。

### 2.4 复现

```bash
node tools/fts5-cjk-bench.mjs --rows 50000  --queries 120
node tools/fts5-cjk-bench.mjs --rows 200000 --queries 120 --seed 20261012
```

## 4. 第 3、4 项：权威性与部署

### 4.1 第 3 项：权威数据职责（已写入 `data-model.md` §1.1）

| 角色 | 是什么 | 不是什么 |
| --- | --- | --- |
| **SQLite 数据库** | 设备本地的**持久化载体** | 不是"唯一的权威"，只是承载权威数据的容器 |
| **`op` 操作日志** | **唯一的变更事实来源**；同步、重放、审计都依据它 | 不是缓存，不可丢弃 |
| **物化业务表** | 当前状态的**物化表示**，由 op 推导 | **不是权威**，可由 op 重建；必须与 op 一致（T-DB-REPLAY 守护） |
| **`search_fts`** | 纯索引 | **非权威**，可随时重建 |
| **`audit_log`** | 面向用户的历史视图 | **非权威**，可由 op 重建（→ 建议 S2 懒生成） |
| **relay 服务端** | 变更**传输**与游标管理 | **不是独立业务账本**；不做合并、不做冲突解决 |

### 4.2 第 3 项：补上"长期离线设备 ↔ 日志压缩"的完整规则

评审正确指出：只规定"op 日志保留 90 天"而没有定义离线超过 90 天的设备如何安全恢复。

**已补全（`relay-deployment.md` §6.3–6.4）**：

| 数据 | 保留期 | 理由 |
| --- | --- | --- |
| 客户端 op 日志 | 90 天后压缩为"当前状态 + 关键事件" | 只需本地历史；压缩不移除服务端的删除操作 |
| 客户端墓碑 | **永久** | 防止复活已删数据 |
| **服务端 `server_op`** | **永久**（或用归档 + 全量重同步路径） | 它是所有设备共同的历史来源；删除会让离线设备失去因果信息 |

**关键认识**：客户端压缩是**本地的**，不会把删除操作从服务端抹掉，
所以"客户端压缩"本身**不会**导致离线设备复活数据。
真正的风险来自**服务端**日志被截断。

**若服务端截断，必须走 `resync_required` 路径**，且客户端**绝不**清空本地库重来
（那会在用户不知情下丢掉离线期间的记录），而是：拉取保留起点之后的 op、
照常推送本地未推送的 op、按规则产生冲突记录。

## 8. 第 5 项与第 7 项的交付摘要

### 8.1 第 5 项：隐私与加密（`privacy-encryption.md`）

**核心贡献是把"加密"这个笼统说法拆成四个互相独立的问题**（评审明确要求）：

| 层 | 推荐 | 一句话理由 |
| --- | --- | --- |
| 传输加密 | ✅ **必做** | 成本近零，防住网络窃听 |
| 备份加密 | ⚠️ **可选，默认关闭** | 备份的首要目标是"能恢复"；忘记口令 = 永久丢失 |
| 本地库加密 | ⚠️ **默认关闭，预留开关** | 主要防"设备被拿走"，**防不住已解锁的运行中设备**；与"低记录成本"冲突 |
| 端到端加密 | ❌ **V1 不做** | 与"新设备从零恢复"直接冲突，且忘记密钥=永久不可读 |

**三处关键澄清**：
1. **HTTPS 不是端到端加密** —— 自建 relay 时服务端**能读到日记正文**（`value_json` 明文）。
2. **数据库加密防不住已解锁的设备** —— 用户解锁设备即解锁应用。
3. **换机时钥匙串内容通常不随备份迁移** —— 若密钥只存在钥匙串里，
   用户会得到"备份在手但打不开"的结果（风险 RV-11）。

**V1 的关键要求不是"实现加密"，而是"不要让加密成为将来加不进去的东西"**：
数据库打开路径集中一处、备份/恢复/迁移不假设明文、清单记录加密引擎（§4.5）。

### 8.2 第 7 项：通知、MSIX 与工具链（`platform-toolchain-plan.md`）

- **通知能力矩阵**：两平台 × 权限失败 / 应用关闭后 / 重启后 / 精确投递，
  并给出 `notification_state` 六值映射（强化 R-REM-04 为**五类情形分别呈现**）。
- **统一模型**：尽力而为 + **启动补课**（呈现过期提醒、重排未来提醒、复查权限）。
- **MSIX 结论**：MSIX **解决**"通知可取消 / 可枚举 / 可激活"，
  **不自动解决**"应用关闭后新建提醒"。
  **但 MSIX 可能改变应用数据目录** → 必须先做 **M9 验证**，否则会出现"升级后数据消失"（RV-12）。
- **工具链**：给出本机安装清单 + **可直接使用的 GitHub Actions 配置**
  （`windows-latest` / `ubuntu-latest`），并明确 **CI 不能替代真机验证**
  （通知投递、OEM 省电、MSIX 旁加载、移动端搜索性能都必须真机）。
- **本机网络障碍**：实测 PowerShell/curl 无出网，已给出 `FLUTTER_STORAGE_BASE_URL` 镜像应对。
