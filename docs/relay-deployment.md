# relay-deployment.md — 自建 HTTPS relay 的完整部署方案

> 评审第 4 项要求："优先评估自建 HTTPS relay。请给出服务端技术栈、部署方式、
> 认证、TLS、服务端存储、备份、版本兼容、附件传输、成本与维护要求。
> 必须说明：没有实际可用的服务端时，哪些同步能力只能标记为未完成。"
>
> 用户已决定（Q1）**V1 交付可用的多设备同步**，通道优先自建 HTTPS relay（Q2）。
> 本文件是该决定的落地设计。**注意：设计 ≠ 已部署。** §9 明确列出"未完成"的判定标准。

---

## 1. 设计约束

来自规格与先前决策：

| 约束 | 来源 |
| --- | --- |
| 服务端**不做**合并、不做冲突解决、不做业务规则 | `sync-protocol.md` §6.1 |
| 服务端不成为独立业务账本（只搬运 + 游标） | 评审第 3 项 |
| 传输必须用安全连接 | 规格 §8.5 |
| 必须明确服务端保存什么数据、如何加密、账户如何恢复 | 规格 §8.5 |
| 同步成功 ≠ 备份成功；服务端也要备份 | 规格 §8.3 |
| 默认本地优先；不上传内容用于分析 | 规格 §8.5 |
| V1 可离线使用，恢复联网后继续同步 | 规格 §8.3 |

**单用户、2–3 台设备**是设计前提（规格 §2.2 排除多人协作）。
这允许我们做很多简化：不需要多租户、不需要复杂权限模型、不需要水平扩展。

## 2. 服务端技术栈（推荐）

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 运行时 | **Dart（`dart:io` HttpServer）** 或 Node.js | Dart 可与客户端共享 `op` 的序列化与校验代码，避免两套实现漂移；Node 生态更成熟 |
| 数据库 | **SQLite（单文件）+ WAL** | 单用户 2–3 设备，写入量极低；运维成本接近零；与客户端同源技术栈 |
| 反向代理 | Caddy（自动 HTTPS）或 Nginx + certbot | Caddy 的自动证书续期最省事 |
| 部署形态 | 单容器 / 单二进制 + systemd | 不需要编排 |
| 附件存储 | 本地目录（内容寻址，`blobs/<sha256>`） | 与客户端同构；可后续换对象存储 |

**推荐组合：Dart 服务端 + SQLite + Caddy，部署在任意一台常开机器或低价 VPS。**

选择 Dart 的额外好处：`op` 的 JSON 结构、版本向量比较、HLC 编码可以
**直接从客户端包中导入**，服务端不需要独立实现一套协议解析——
这显著降低"两端协议理解不一致"的风险（`sync-options.md` §4.1 提到的真实成本之一）。

### 2.1 服务端数据库

```sql
-- 全局变更日志：唯一的权威顺序来源
CREATE TABLE server_op (
  seq         INTEGER PRIMARY KEY AUTOINCREMENT,  -- 单调递增，游标基础
  op_id       TEXT    NOT NULL UNIQUE,            -- 幂等键（客户端生成）
  device_id   TEXT    NOT NULL,
  entity_id   TEXT    NOT NULL,
  entity_type TEXT    NOT NULL,
  op_type     TEXT    NOT NULL,
  field       TEXT,
  value_json  TEXT,
  strategy    TEXT,
  vv_json     TEXT    NOT NULL,
  hlc_p       INTEGER NOT NULL,
  hlc_l       INTEGER NOT NULL,
  hlc_d       TEXT    NOT NULL,
  received_at INTEGER NOT NULL
) STRICT;
CREATE INDEX idx_server_op_seq ON server_op(seq);

-- 设备注册与授权（见 §4）
CREATE TABLE device (
  device_id     TEXT NOT NULL PRIMARY KEY,
  label         TEXT NOT NULL,
  token_hash    TEXT NOT NULL,          -- 只存哈希，不存明文
  created_at    INTEGER NOT NULL,
  last_seen_at  INTEGER,
  revoked_at    INTEGER
) STRICT;

-- blob 元数据（本体在文件系统）
CREATE TABLE blob (
  sha256      TEXT NOT NULL PRIMARY KEY,
  bytes       INTEGER NOT NULL,
  uploaded_at INTEGER NOT NULL
) STRICT;
```

**注意没有 `conflict` 表**——冲突由客户端从 `op` 推导（`data-model.md` §2.5），
服务端只搬运 op。这是"服务端不成为业务账本"的具体体现。

### 2.2 API（最小集合）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/v1/push` | 批量提交 op；`INSERT OR IGNORE`，返回每条 op 的 `seq` |
| `GET` | `/v1/pull?since=<seq>&limit=200` | 游标拉取；返回 `ops`、`next_cursor`、`has_more` |
| `PUT` | `/v1/blob/<sha256>` | 上传附件（幂等，已存在返回 200） |
| `GET` | `/v1/blob/<sha256>` | 下载附件 |
| `GET` | `/v1/health` | 健康检查（含 schema 版本） |
| `GET` | `/v1/capabilities` | 协议版本与限制，供客户端协商（§7） |

**极简性的意义**：整个服务端逻辑约 400–600 行（含路由与校验），
不含认证与部署。参考实现在原型中只有 **75 行**（`prototype/sync-core/src/relay.js`）。

## 3. 部署方式

### 3.1 三种可选形态

| 形态 | 适用 | 成本 | 隐私 |
| --- | --- | --- | --- |
| **A. 用户自有机器**（家中常开 PC / 树莓派 / NAS，配 Tailscale 之类组网） | 重视隐私、已有常开设备 | 电费 | **数据不出自有网络** |
| **B. 低价 VPS** + Caddy | 需要随时随地访问 | 约 $4–6/月 | 数据在 VPS 上（§8 讨论） |
| **C. 局域网直连**（无公网 relay） | 只在家中多设备同步 | 零 | 最好，但离线跨网络不能同步 |

**推荐 V1 先交付形态 A 或 B；形态 C 作为 `FileFolderAdapter` 之外的降级选项。**

### 3.2 部署步骤（形态 B）

```bash
# 1) 构建（单二进制或单容器）
dart compile exe bin/relay.dart -o relay        # 或 docker build

# 2) 数据目录（务必在持久卷上，且不放在云盘同步目录！）
sudo mkdir -p /var/lib/life-relay/{db,blobs}
sudo chown -R liferelay:liferelay /var/lib/life-relay

# 3) 配置 Caddy（自动申请与续期证书）
#    /etc/caddy/Caddyfile
#    sync.example.com {
#        reverse_proxy 127.0.0.1:8787
#    }

# 4) systemd 单元（关键：备份与崩溃恢复）
#    /etc/systemd/system/life-relay.service
#    [Service]
#    ExecStart=/usr/local/bin/relay --data /var/lib/life-relay --port 8787
#    Restart=always
#    RestartSec=2

# 5) 启动与验证
sudo systemctl enable --now life-relay
curl https://sync.example.com/v1/health
```

**必须强调**：服务端数据目录**同样不能放在通用云盘同步目录**，
原因与风险 DL-1 相同（SQLite + WAL 撕裂）。这是很容易犯的错误，
因为"VPS 上放哪都行"的直觉是错的。

## 4. 认证与设备授权

单用户场景**不需要**完整的账户系统，但**必须**防止任意人读写你的日记。

### 4.1 方案：预共享令牌 + 设备注册

```
1. 服务端启动时生成一个注册密钥（registration secret），只显示一次
2. 每台设备首次同步时用注册密钥换取自己的 device token
3. 服务端只存 token 的哈希（如 SHA-256）
4. 后续请求用 `Authorization: Bearer <device-token>`
5. 服务端记录 device_id ↔ token 绑定；可单独吊销某台设备
```

| 要求 | 实现 |
| --- | --- |
| 令牌不落明文 | 服务端只存哈希；客户端存 `flutter_secure_storage`（Windows 凭据管理器 / Android Keystore） |
| 设备可吊销 | `device.revoked_at`；吊销后该 token 立即失效（丢失手机的场景） |
| 防重放 | TLS 已覆盖；op 本身幂等所以重放无害 |
| 越权访问其他设备数据 | V1 是单用户，所有设备共享同一数据空间；**不**需要隔离 |
| 暴力破解 | 注册密钥仅用于首次注册；注册后可关闭注册端点 |

**明确不做**（V1）：OAuth、多用户、共享空间、细粒度权限（规格 §2.2 排除）。

### 4.2 令牌轮换与恢复

| 场景 | 处理 |
| --- | --- |
| 手机丢失 | 服务端吊销该 `device_id`；其他设备不受影响 |
| 忘记注册密钥 | 服务端可重新生成（需要能登录服务器的管理员权限） |
| 新增设备 | 用注册密钥注册；**不需要**重新上传全部数据（拉取游标从 0 开始即可） |
| 全部设备丢失 | 数据只在备份里——**这就是同步不能替代备份的原因** |

## 5. TLS

| 项 | 要求 |
| --- | --- |
| 最低版本 | **TLS 1.2**，推荐 1.3 |
| 证书 | Let's Encrypt（Caddy 自动）或用户自有证书 |
| HSTS | 启用 |
| 明文 HTTP | **禁止**（客户端应拒绝非 HTTPS 端点，除非显式配置为本地网络模式） |
| 证书校验 | 客户端必须校验证书；**不得**提供"跳过证书校验"的常规选项 |
| 自签名证书 | 仅允许用户显式导入信任（形态 A 的自建场景），并在 UI 标注风险 |

**本地网络模式（形态 A/C）的例外**：若 relay 只在局域网内且用户明确选择该模式，
允许 http 但**必须在 UI 明确标注"未加密传输"**，且默认不开启。

## 6. 服务端存储、容量与备份

### 6.1 容量估算

| 数据 | 估算 | 依据 |
| --- | --- | --- |
| 单条 op | 约 300–600 字节（JSON + 索引开销） | 字段级 op 含 vv/hlc/strategy |
| 每天 50 次操作/设备 × 2 设备 | 约 100 op/天 ≈ 40 KB/天 | |
| 一年 | 约 15 MB | |
| 十年 | 约 150 MB | 对 SQLite 完全无压力 |
| 附件 | 取决于用户；50 MB/文件上限 | 需求 ⚠GAP-21 |

**结论**：单人规模下服务端存储压力极小。真正的容量风险是**附件**和
**变更日志永不删除**（见 §6.3）。

### 6.2 服务端备份（必须做）

规格 §8.3 明确"同步成功不等于备份成功"，服务端也一样：

| 项 | 要求 |
| --- | --- |
| 方法 | `VACUUM INTO`（与客户端同一套一致性快照方法，`backup-restore.md` §2.3） |
| 频率 | 每日 + 每次版本升级前 |
| 保留 | 最近 14 份 + 每月 1 份保留 1 年 |
| 异地 | 至少一份在服务器之外（对象存储或用户下载） |
| **恢复演练** | 必须实际演练过（规格 §8.4 的精神同样适用于服务端） |
| blob | 与数据库分别备份；blob 是内容寻址的，增量备份容易 |

### 6.3 变更日志的保留（与本地压缩的关系，评审第 3 项）

**关键问题**：客户端本地 op 日志 90 天后压缩（`decisions/0005`），
但**服务端日志必须保留更久**，否则长期离线的设备无法正确追赶。

| 数据 | 保留期 | 理由 |
| --- | --- | --- |
| 服务端 `server_op` | **永久**（或至少 ≥ 墓碑的"永远"） | 离线一年的设备可能从 `seq=0` 重新拉取；删除日志会导致它看不到删除操作 |
| 服务端墓碑 | 由 op 日志承载，同样永久 | 同上 |
| 客户端 op 日志 | 90 天后压缩 | 客户端只需要"当前状态 + 关键事件"，压缩后仍能作为本地历史 |
| 客户端墓碑 | 永久 | 防止复活已删数据 |

**为什么服务端不能跟着压缩**：客户端压缩是**本地的**，
它不会把"删除操作"从服务端抹掉。服务端日志是**所有设备共同的历史来源**，
删除它等于让离线设备失去因果信息。

**空间代价**：§6.1 估算十年约 150 MB，可接受。
若用户担心，提供"服务端日志归档"选项（导出后截断），
但必须明确：**截断会使早于该点的离线设备无法安全追赶**，
届时客户端必须走"全量重新同步"路径（见 §6.4）。

### 6.4 长期离线设备与全量重同步（评审第 3 项的核心）

这是评审正确指出的一个未闭合缺口。完整规则：

```
设备 D 离线很久后上线：
  if 服务端仍保有 D 的游标之后的所有 op:
      正常增量拉取                      → 完成
  else if 服务端日志被截断/归档，D 的游标早于保留起点:
      服务端返回 `resync_required` + 保留起点 seq
      客户端进入「全量重同步」：
        1. 不删除本地数据（避免丢数据）
        2. 从保留起点开始拉取，把远端 op 应用到本地
        3. 本地独有的、尚未推送的 op 照常推送（幂等）
        4. 与远端冲突的按 §4.1 产生冲突记录
      结果：本地数据要么被保留，要么进入冲突列表，**不静默丢失**
```

**必须有的两条保障**：
1. 服务端**不主动删除** op；只有在用户显式归档时才截断，且截断前必须备份。
2. 客户端遇到 `resync_required` 时**绝不**清空本地库重来——
   那会在用户不知情的情况下丢掉离线期间的记录。必须走上述合并路径。

**待定（需用户决策 Q13）**：是否接受"服务端 op 日志永久保留"（推荐），
或接受"归档策略 + 全量重同步路径"的复杂度。

## 7. 协议版本兼容

| 项 | 设计 |
| --- | --- |
| 协议版本 | `op` 批次携带 `protocol_version`；服务端在 `/v1/capabilities` 声明支持范围 |
| 兼容策略 | **服务端向后兼容旧客户端**（新字段可选，未知字段忽略）；服务端升级不要求客户端同时升级 |
| 客户端过旧 | 若服务端不再支持该版本，返回 `426 Upgrade Required` + 最低支持版本；客户端显示明确提示（不静默失败） |
| 服务端过旧 | 若客户端需要新能力而服务端不支持，降级到可用子集，并在 UI 标注"同步服务需要升级" |
| 不兼容变更 | 通过 `/v2/` 路径并行提供，而非原地破坏 |
| schema 版本 | 服务端 `/v1/health` 返回自身 schema 版本，便于运维 |

**关键原则**：协议升级**不得**要求用户同时升级所有设备。
`op` 格式的演进必须是"加可选字段"式的，不是"改字段语义"式的。

## 8. 隐私边界（服务端能看到什么）

这是必须向用户如实说明的（规格 §8.5、§8.8）：

| 项 | V1 状态 |
| --- | --- |
| 传输加密 | ✅ TLS |
| 服务端存储加密 | ❌ 默认**没有**。数据库与 blob 在服务器磁盘上是明文（依赖磁盘加密） |
| 服务端能否读取日记正文 | ⚠️ **能**。`server_op.value_json` 含明文字段值 |
| 端到端加密（服务端不可读） | ❌ V1 不提供。需要额外设计（见 §8.1） |

### 8.1 若要"服务端不可读"，需要什么

| 方案 | 代价 |
| --- | --- |
| 客户端加密字段值后再同步 | 服务端无法做任何服务端搜索（V1 本来也不需要）；需要密钥在设备间安全分发；密钥丢失 = 数据不可读；**无法支持"新设备从零恢复"除非用户另行保管密钥** |
| 仅加密敏感字段（日记正文） | 需定义"敏感"边界；元数据（时间、标签）仍泄露；查询与搜索在客户端做（本来也是） |

**推荐**：V1 保持明文（配合 TLS + 磁盘加密 + 自建/自有服务器），
把 E2E 列为 V2 候选，并在文档与 UI 明确说明**当前服务端可读**。
**不得**在宣传中说"端到端加密"。

### 8.2 日志与可观测性

- 服务端日志**不得**记录 `value_json` 内容（规格 §8.5 同精神）。
- 只记录：请求计数、字节数、错误码、device_id、seq 范围。
- 提供日志保留期设置（默认 30 天）。

## 9. 成本与维护要求

### 9.1 成本

| 项 | 形态 A（自有机器） | 形态 B（VPS） |
| --- | --- | --- |
| 硬件/租金 | 已有设备 | $4–6/月（约 ¥30–45） |

### 9.2 维护要求（评审要求明确列出）

| 任务 | 频率 | 说明 |
| --- | --- | --- |
| 系统与依赖安全更新 | 每月 | 主要风险来源 |
| 证书续期 | 自动（Caddy） | 但需监控失败 |
| 服务端备份验证 | 每月 | 不能只看备份文件存在 |
| 服务端恢复演练 | 每季度 | 与客户端同样要求 |
| 容量检查（附件增长） | 每季度 | |
| 协议/客户端版本兼容检查 | 每次客户端发布 | |
| 服务可用性处理 | 按需 | 服务不可用时客户端离线工作，恢复后继续 |

**这不是"部署一次就不用管"的系统。** 用户需要明确接受这是持续性运维投入。
如果用户不愿承担，则应选择形态 C（局域网，无公网服务）并接受"跨网络不能同步"的限制。

## 10. 没有服务端时，哪些能力必须标记为未完成

评审明确要求说明这一点。以下判定**写入 `known-limitations.md`**：

| 能力 | 有可用 relay | 无可用 relay（仅接口） |
| --- | --- | --- |
| 单设备记录、搜索、备份 | ✅ | ✅ |
| 同一局域网文件交换同步（`FileFolderAdapter`，需用户在可用存储上协作） | — | ⚠️ 可用但**有明确限制**：无全局单调 seq，多设备并发写同一目录需要额外协调；仅建议 2 台设备 |
| 跨网络自动同步 | ✅ | ❌ **未完成** |
| 双设备端到端同步测试（规格 §10.3 旅程 E） | ✅ 可验证 | ❌ **无法验证** |
| 附件跨设备传输 | ✅ | ❌ 未完成 |
