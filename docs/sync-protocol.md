# sync-protocol.md — 设备、变更、冲突、重试与墓碑规则

> 本文件是规格 §8.3 要求的同步协议设计，必须在编码前完成。
> 协议语义已由可执行原型 `prototype/sync-core/` 验证（**33/33** 测试通过，见 §9）。

## 1. 设计目标与非目标

**目标**
1. 离线优先：任意设备可长期离线写入，恢复联网后收敛。
2. 幂等：重复推送/重复应用不产生重复数据。
3. 不静默丢改：同一对象的并发修改必须可见——要么无损合并，要么产生**用户可见、可解决**的冲突记录。
   见 §4.1（评审修订：原方案只对文本字段做到了这一点）。
4. 删除可靠传播：删除不被旧数据"复活"。
5. 可重试、可观测：任何失败可见、可重试、可诊断。

**非目标（V1）**
- 不做实时协同编辑（不需要 OT/CRDT 文本合并）。
- 不做服务端权威校验与业务规则。
- 不做多用户/权限/共享空间（§2.2）。

## 2. 数据单位：`op`（操作）而非"行"

同步搬运的是 `op`，不是表行。原因：
- 行级覆盖会丢弃同对象不同字段的并发修改（§8.3 禁止）。
- op 是追加不可变的，天然适配"游标拉取 + 幂等应用"。
- op 同时充当审计与撤销的依据（§9.8）。

`op` 字段见 `data-model.md` §2.2。核心：

| 字段 | 作用 |
| --- | --- |
| `op_id` | UUIDv7，**全局唯一且是幂等键**（服务端唯一约束） |
| `entity_id` / `entity_type` | 目标对象 |
| `op_type` | `create` / `set` / `set_add` / `set_remove` / `delete` / `restore` |
| `field` | 字段级并发控制的粒度 |
| `value_json` | 值 |
| `strategy` | 该字段的合并规则（冗余，真正权威是 `field_schema`） |
| `vv_json` | 版本向量 `{deviceId: counter}` |
| `hlc_{p,l,d}` | 混合逻辑时钟 |
| `local_seq` | 本设备产生顺序，用于出站排序 |

**字段级（而非行级）是核心决策。** 两台设备分别改 `title` 与 `due_at`，
必须两个修改都保留——行级 LWW 会丢掉一个。

## 3. 时钟与排序

### 3.1 为什么不用墙钟

设备时钟会错、会被用户改、会跨时区跳变。用墙钟做 LWW 会导致
"时钟慢的设备永远覆盖不了时钟快的设备"或反之（静默丢改）。

### 3.2 HLC（混合逻辑时钟）

`hlc = (p: 物理毫秒, l: 逻辑计数, d: 设备ID)`，比较顺序 `p → l → d`。

- 本地事件：`tick()` 若墙钟前进则 `(wall, 0)`，否则 `(p, l+1)`，**保证本设备单调**。
- 收到远端：`observe(remote)` 把本地 `p` 推到 `max(本地p, min(远端p, 墙钟+最大偏移))`，`l = max(...)+1`。
  这保证因果一致（"看到过 A 的修改"这件事被编码进时钟），同时**防住未来时钟**：
  远端时间超过 `墙钟 + 1 小时` 时被截断并触发 `skewWarning`，避免一台时钟跑到 2050 年的设备
  把系统时间永久推走。

- `hlc.d` 参与比较，保证两台设备同一毫秒的并发写有**确定性**胜者。
- 最终并列时用 `value_hash` 再比，最后用 `op_id` 兜底——**任意设备、任意顺序，结果一致**。

### 3.3 版本向量（因果判定）

`vv = {deviceId: counter}`，**每个字段一份**（`field_register.vv_json`）。

- 写该字段时 `vv[自己] += 1`。
- 应用/观察远端 op 时 `vv = 逐分量 max(vv, op.vv)`（**即使该 op 落败也要合并**，
  否则下一轮会把它误判为并发）。

比较结果：

| `vv_compare(op.vv, local.vv)` | 含义 | 动作 |
| --- | --- | --- |
| `dominates` | 远端因果更新 | 应用 |
| `equal` | 同一向量（可能重复投递） | 用总序（HLC→hash→op_id）判胜负 |
| `dominated` | 远端是旧的 | 丢弃（保留在 op 日志中） |
| `concurrent` | **真并发** | 按策略：lww 用总序；text 保留两版；set 逐元素 |

> 只用 HLC 而不用版本向量也能"看起来能用"，但会把
> 「B 已看到 A 的修改后再改」误判为冲突。原型有专门测试
> （`conflict: a causally-later edit is NOT reported as a conflict`）守护。

### 3.4 时间戳与时区（§4.5 要求）

- **瞬时**（`due_at`、`start_at`、`remind_at`）：存 **UTC epoch 毫秒** + `tz_id`（IANA）。
- **本地日期**（`scheduled_date`、`journal_date`）：存 `YYYY-MM-DD` 字符串 + 设备 `tz_id`。
  **不**把"某天"换算成瞬时，否则 DST / 跨时区会漂移一天。
- 展示一律经 `TZDateTime`；**禁止**对 UTC 毫秒做 `Duration(days: 1)` 运算
  （DST 会让"一天"变成 23 或 25 小时）。
- 提醒锚定**瞬时**而不是墙上时间：夏令时"春季跳过"会产生不存在的本地时刻
  （02:30 不存在），锚定瞬时可避免提醒丢失。
- 时区数据库版本记入备份清单（`manifest.json`），因为规则变化会重新解释历史本地时间。

## 4. 合并策略（按字段声明，见 `field_schema`）

> **本节经设计评审修订。** 原方案只对 `text` 字段产生用户可见的冲突记录，
> `lww` 字段"总序取一个胜者、落败值只留在 op 日志"——这与本文开头的承诺
> "同一对象的并发修改必须可见"**直接矛盾**。例如 Windows 标记任务 `done`、
> Android 同时标记 `cancelled`，用户只会看到一个结果，永远不知道另一个存在。
> 修订后的规则见 §4.1。

| 策略 | 适用 | 并发时的行为 | 用户可见结果 |
| --- | --- | --- | --- |
| `lww` | 状态、日期、时刻、分类、单值 FK | 总序取一个胜者，**落败值写入 `conflict` 表** | **对象详情出现冲突提示**，可查看落败值并选择保留哪一版 |
| `text` | 标题、正文、描述 | 同上，且两版正文都保留在冲突记录中 | 同上；`both_versions_retained = true` |
| `set` | 标签、多值关系、附件引用 | 逐元素：`(HLC, 设备)` 决胜；元素带 `present` 墓碑 | 两侧新增都保留；删除不被复活 |

**没有 additive 策略。** 计数类一律派生（查询时算），绝不做跨设备求和——
重复投递会重复计数。

### 4.1 冲突可见性规则（评审修订的核心）

**触发条件（必须同时满足）：**

1. 两个写入是**真并发**的（版本向量互不支配，见 §3.3）；
2. 两边的**值不同**。

**明确不触发冲突的情况：**

- 因果更晚的写入（"B 看到了 A 的修改后才改"）——这是普通编辑；
- 并发但**值相同**（两台设备都设为 `done`）——无事可报；
- 顺序编辑——即使用户来回改 20 次也不会产生冲突。

这条"值不同才算冲突"的限定很重要：如果没有它，正常编辑会淹没在冲突提示里，
用户就会开始忽略提示，真正的冲突反而被漏掉（风险 CC-3）。

**冲突记录的要求：**

| 要求 | 实现 |
| --- | --- |
| 稳定 | `conflict_id = hash(losing_op, winning_op, field)`，确定性生成 |
| 可同步 | 冲突由**两边各自从 op 推导**得出，不需要同步 conflict 行本身；因此不存在"冲突表同步"这一额外协议 |
| 可去重 | 确定性 id + 唯一约束；重复投递不产生新行 |
| 跨设备一致 | 两台设备观察同一次冲突时，`conflict_id`/`losing_op`/`winning_op`/`losing_value` **完全相同** |
| 可见 | 计入"待处理"计数；对象详情页显示提示，直到用户显式处理 |
| 可解决 | `resolveConflict(keep_winner / keep_loser / custom)` |

**解决冲突 = 写一条普通的 `set` op。** 这是刻意的设计：
解决动作复用已经过测试的版本向量 + 总序机制，因此它天然可同步、可收敛，
不需要另建一套"冲突解决协议"。

**冲突何时关闭（S1，用户已批准：显式同步解决记录）：**

关闭**不再是各设备本地推导的状态**，而是一条显式 op：

| 项 | 设计 |
| --- | --- |
| 载体 | `op_type = 'resolve_conflict'`；`field` 列承载 `conflict_id`；`value` 承载选择 |
| 生成 | `resolveConflict()` 在解决设备上生成，带全局唯一 `op_id` |
| 幂等 | 同一 `conflict_id` 只允许一条解决 op（`UNIQUE INDEX ... WHERE op_type='resolve_conflict'`） |
| 传播 | 作为普通 op 推送/拉取，因此**所有设备看到同一条解决记录** |
| 收敛 | 每台设备从 op 日志**派生** `resolved_at`/`resolution`/`resolution_op` 等展示字段 |
| 同时写入的值 | `keep_loser` / `custom` 会额外写一条普通值 op；`keep_winner` **只写解决 op**（值不变） |

> **为什么必须显式**：`keep_winner` 不改变字段值，其他设备**没有任何可观察的信号**，
> 于是冲突会在它们那里长期显示待处理。这是原"派生关闭"方案的实质缺陷——
> 已由设计评审指出并修复。实现与测试见
> `prototype/sync-core/test/conflict.test.js` 的
> `keep_winner emits ONLY a resolution op` 与
> `keep_winner resolution propagates and closes the conflict everywhere`。
>
> **解决记录本身不需要单独的表同步协议**：它就是 `op` 的一种类型，
> 复用已经过测试的幂等、重试、游标与收敛机制。

### 4.2 落败写入仍必须合并版本向量（评审发现的潜在缺陷）

丢弃一个落败写入时，**必须**把它的版本向量合并进 `field_register`。否则有两个后果：

1. 该 op 在之后每次同步时都被重新评估、重新丢弃（浪费且难排查）；
2. 更严重：一旦第三台设备的写入到达，被丢弃的值**在原理上都无法再恢复**，
   因为寄存器已不知道"曾观察到这个落败版本"。

原型中这是真实存在的 bug，修复后有专门测试
（`review: a discarded losing write still merges its version vector`）。

### 4.3 冲突记录 id 为什么必须哈希"两侧"

同一次冲突会在两台设备上各被观察一次（赢方应用落败 op 时、输方应用获胜 op 时）。
若只以某一侧为键，两侧会推导出字段互换的两条记录，冲突列表**本身不收敛**。
对 `(落败 op, 获胜 op, 字段)` 三者取哈希后，两处推导出的记录完全一致。

> 这是原型开发中**实际踩到的两个 bug 之一**：
> ① `orderOps` 的最终并列判据读的是 `op.op_id`，而字段寄存器里叫 `opId`，
> 寄存器与 op 比较时该判据静默失效；
> ② `snapshot()` 只读 `opId`，因此对**传入 op** 取快照时 `opId` 恒为 `undefined`，
> 而 JSON 会丢掉 undefined 字段——冲突记录因此**丢掉了 `losing_op`**，
> 既无法解决也无法收敛。两者都已修复并有测试守护。

### 4.4 `field_schema` 必须"先声明后使用"

原型实测第三个 bug：若允许"第一次写某字段时注册策略"，
那么任何提前触碰该字段的代码路径（例如 `createEntity` 写初始值）会把它
**永久钉死在默认 LWW**，之后真正的 `text` 声明就会与之冲突。
因此：策略在启动时按实体类型声明进 `field_schema`，**未声明字段的写入直接抛错**。

### 4.5 HLC 观测必须在 `applyOp` 内完成

排序正确性依赖"本地 HLC 已吸收所有见过的远端时间戳"。
原实现把这个副作用放在 `pull()` 里，于是任何**其他**调用路径
（重试逻辑、手动重放、测试）都会在未推进时钟的情况下应用 op，
导致传入写入被错误排序——产生虚假冲突，极端情况下让旧值获胜。
修订后 `observeRemoteClock` 成为 `applyOp` 的一部分，从结构上消除该隐患
（对本地 op 幂等）。

## 5. 各对象类别的冲突策略（规格 §8.3 明确要求）

规格原文要求"任务状态、时间记录、标签和关系需要有明确冲突策略"。
下表是**修订后**的策略：所有 `lww` 类别在真并发且值不同时同样产生**用户可见冲突**（§4.1）。

| 类别 | 策略 | 并发且值不同时用户看到什么 | 理由 |
| --- | --- | --- | --- |
| 任务状态 | `lww` + 冲突可见 | 冲突提示："另一台设备改为 cancelled"，可选择保留哪一版 | "done 与 cancelled"无法折中，但**必须让用户知道**；`previous_status` 支持回退 |
| 任务标题/描述 | `text` + 两版保留 | 冲突提示，两版正文都可查看 | 用户写下的文字不能悄悄丢 |
| 时间记录 `start_at`/`end_at` | `lww` + 冲突可见 | 冲突提示，落败区间可查看 | 区间必须自洽，合并两个区间会产生无意义的第三区间；但落败版本必须可见可恢复 |
| 时间记录 `timer_state` | `lww` | 见 §5.1 | |
| 标签 | `set`（并集 + 逐元素墓碑） | 无冲突（两侧新增都保留） | 两台设备各自打不同标签都必须保留 |
| 关系 | `set`（同上） | 无冲突 | 解除关系是 `set_remove`，不删除对象 |
| 收集记录 `content` | `text` | 冲突提示 | 原始记录是最不可再生的数据 |
| 收集记录状态 | `lww` + 冲突可见 | 冲突提示 | |
| 日记正文 | `text` | 冲突提示 | 同一天多篇本就是不同对象，不冲突（§4.7） |
| 附件引用 | `set` | 无冲突 | |

**判定"值不同"用的比较**：结构化相等（对象/数组按规范化 JSON 比较），
不是引用相等——否则两个内容相同的对象会被误判为冲突。

### 5.1 计时器的并发语义

两台设备可能各自在计时——这是**合法**的，不是冲突。
`time_entry` 的 `timer_state='running'` 唯一索引是**每设备局部**的
（同步来的 running 行不参与本机唯一约束判断，见 `data-model.md` §3.5）。
本机启动计时时若已有本机 running 行，用例层要求先结束或提示。

**绝不允许**在同步合并时"自动结束对方的计时器"——那会伪造结束时间（§4.5 禁止）。
若两台设备对**同一个** `time_entry` 的 `end_at` 产生并发写入，则按上表产生可见冲突。

## 6. 传输与游标

### 6.1 服务端模型

relay 只做三件事，**不合并、不解决冲突**：

1. `push(ops[])`：`INSERT OR IGNORE INTO server_op(op_id UNIQUE, ...)`，
   为每条新 op 分配**单调递增** `seq`；已存在的 `op_id` 直接返回原 `seq`（幂等）。
2. `pull(since, limit)`：`WHERE seq > since ORDER BY seq LIMIT limit`，返回 `next_cursor` 与 `has_more`。
3. `uploadBlob` / `downloadBlob`：内容寻址（sha256），天然幂等、天然去重。

### 6.2 客户端循环

```
SyncNow:
  1. PUSH  outbox 中 local_seq 升序的前 N 条（默认 200）
          ├─ 每条 ack 才从 outbox 删除
          └─ 部分失败 → 整批重试（服务端唯一约束保证不重复）
  2. PULL  since = sync_cursor.applied_seq
          对每页：BEGIN
                    apply 每条 op（幂等）
                    UPDATE sync_cursor SET applied_seq = page.next_cursor
                  COMMIT
  3. 附件：按缺失 blob 拉取（见 §7）
```

**游标与变更在同一事务内提交**——这是崩溃安全的关键。
若先提交变更再写游标，崩溃后重放是安全的（幂等）；但反过来（先写游标）会**永久丢数据**。

### 6.3 分页与批量

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| push 批量 | 200 ops | 过大则单次失败代价高 |
| pull 分页 | 200 ops | |
| 单 op 上限 | 256 KB | 超出走 blob（附件） |
| 重试退避 | 1s, 2s, 4s … 上限 5min + 抖动 | 抖动避免多设备同拍 |
| 网络要求 | 仅 HTTPS/WSS | §8.5 要求安全连接 |

### 6.4 Sync Adapter 接口（规格 §8.3 明确要求可替换）

```dart
abstract interface class SyncTransport {
  String get peerId;                     // 参与游标标识
  Future<PushResult> push(List<Op> ops);
  Future<PullPage> pull({required int since, int limit = 200});
  Future<void> uploadBlob(String sha256, Stream<List<int>> bytes);
  Future<Stream<List<int>>> downloadBlob(String sha256);
}
```

V1 实现：

| 适配器 | 通道 | 定位 |
| --- | --- | --- |
| `HttpRelayAdapter` | 自建 HTTP 服务 | 主方案（需用户提供/自建） |
| `FileFolderAdapter` | 用户指定的同步目录（每设备一个追加文件 + 服务端 seq 由**本地重放分配**） | 无服务端的降级方案；明确记录其"无全局单调 seq"限制 |
| `NoopSyncAdapter` | 无 | 单设备模式；UI **必须**明确显示"同步未启用" |

> 规格 §8.3 最后一段的约束：如果最终没有可用的同步服务，
> 就交付 Adapter 接口 + 单设备功能，并**不得**宣称多设备同步已完成。
> 这正是 `known-limitations.md` 必须记录的内容。见需求 ⚠GAP-02 / 问题 Q1。

## 7. 附件同步

- 附件**本体不进 op 日志**，只同步 `attachment_meta` + `blob.sha256`。
- 上传/下载按内容寻址，天然幂等与去重（同内容只传一次）。
- 设备缺失某 blob 时，引用处显示"内容未下载"，提供按需拉取按钮（§4.9 失效状态语义）。
- 大文件传输**不阻塞**变更同步：优先保证文本数据一致。
- 删除策略：只解引用，不立即删 blob；孤儿 blob 保留 30 天后清理（`data-model.md` §7）。

## 8. 墓碑

- 删除 = 写入 `op_type='delete'`（带 HLC 与 vv）+ `entity.deleted_at` + `entity.delete_hlc`。
- `entity` 行**永久保留**（体积约 100 字节）：离线设备一年后上线时，
  若墓碑已清理，其旧数据会**复活**已删除对象。
- 内容字段在硬删除时清空，仅保留身份与时间信息。
- **删除 vs 并发编辑**：若编辑的 HLC 在 `delete_hlc` 之前且未见过删除 → 删除生效，编辑进审计；
  若编辑因果上晚于删除 → 视为"恢复"意图，生成 `restore` op 并**明确提示用户**（不静默复活）。

**保留期（需用户确认，问题 Q3）**：墓碑永久；软删除对象 180 天；op 日志 90 天后压缩。

### 9.3 原型发现并修复的真实设计缺陷

这些是"只写文档"不会发现的；括号内是对应的守护测试：

1. **合并策略未持久化** → 重放 op 时丢失 `text` 语义，文本冲突被降级成静默覆盖。
   修正：`field_schema` 表 + op 上冗余 `strategy`。（测试 7）
2. **策略"先写后声明"** → 提前写初始值的代码路径把字段永久钉死在 LWW。
   修正：必须先声明；未声明字段写入抛错。（测试 7）
3. **冲突记录以"观察时刻"为键** → 两台设备的冲突列表字段互换、不收敛。
   修正：对 `(落败 op, 获胜 op, 字段)` 取哈希作唯一键。（测试 27）
4. **`orderOps` 的最终并列判据读错字段名** → op 用 `op_id`、寄存器用 `opId`，
   寄存器与 op 比较时该判据**静默失效**，总序失去最后一级确定性。
   修正：统一取 `opIdOf(x)`。（测试 21、27）
5. **`snapshot()` 只读 `opId`** → 对传入 op 取快照时 `opId` 恒为 `undefined`，
   JSON 又丢掉 undefined 字段，于是冲突记录**丢失 `losing_op`**，既无法解决也无法收敛。
   修正：`snapshot` 同时接受 `op_id`/`opId`，并对缺失 op id 直接抛错而不是静默写入。
   （测试 21、22、28）
6. **落败写入未合并版本向量** → 落败 op 被无限重评估；第三台设备写入后，
   被丢弃的值在原理上不可恢复。修正：无条件合并版本向量。（测试 31）
7. **`observeRemoteClock` 只放在 `pull()` 内** → 任何其他 apply 路径
   （重试、手动重放）都会在未推进 HLC 的情况下应用 op，导致错误排序与虚假冲突。
   修正：观测移入 `applyOp`。（测试 26）
8. **冲突在创建的同一毫秒被自动关闭** → 用"支配落败向量"作为自动关闭判据时，
   获胜方自己应用该写入就把冲突关掉了，用户永远看不到。
   修正：自动关闭还要求当前寄存器 op **既非落败也非获胜**。（测试 21）

> 第 4/5/6/7/8 项都是在**修复评审第 1 项的过程中**发现并修复的——
> 说明"把承诺写成可执行测试"确实能暴露文档评审看不到的问题。

## 10. 失败可见性（§9.12）

| 失败 | 数据状态 | UI |
| --- | --- | --- |
| 网络失败 | op 留在 outbox，游标不动 | "离线，N 项待同步"，可手动重试 |
| 服务端 5xx 部分成功 | 已接受的部分 ack，其余留在 outbox | "部分同步成功"，显示详情 |
| 服务端拒绝（例如 op 过大） | op 留在 outbox 并标记错误 | 明确错误原因 + 处理建议 |
| 应用 op 时抛异常 | 事务回滚，游标不推进 | "同步中断"，可重试，**不得**静默跳过 |
| 时钟偏移检出 | 正常合并 | 提示"设备 X 时间不准确"（不阻断） |
| 附件缺失 | 元数据已同步，blob 标 `missing` | 引用处显示"内容未下载"占位 |

**绝不**出现"显示已同步但实际未同步"。每次同步结果都要落到 `sync_cursor.last_error` 与 UI 状态。
