# search-cjk-results.md — 中文全文搜索方案实测结果

> 评审第 6 项要求："使用至少 5 万条混合中英文测试记录，比较 `trigram`、短查询回退和
> 子串匹配方案的召回率、查询延迟、索引体积与重建耗时。提交实测结果，
> 不要提前宣称中文搜索已经可用。"
>
> **本文件全部数字来自本机实际执行**，脚本 `tools/fts5-cjk-bench.mjs`，可复现：
> ```
> node tools/fts5-cjk-bench.mjs --rows 50000  --queries 120
> node tools/fts5-cjk-bench.mjs --rows 200000 --queries 120
> ```
> 运行环境：Windows 10 Pro 25H2，Node v26.5.0，**SQLite 3.53.3**（`node:sqlite` 内置）。
> 语料：确定性伪随机生成（seed 20261012），45% 纯中文、25% 纯英文、30% 中英混排。
> 查询：从语料中抽取的真实子串，真值由**精确子串成员判断**独立计算，
> 因此召回率是测量的而非假设的。

---

## 1. 结论（先给答案）

**推荐：`trigram` 索引 + 查询串不足 3 字符时回退 `LIKE` 子串匹配。**

实测依据：
- `trigram` 在**所有**查询长度上都达到 **100% 召回与 100% 精确**（107/107 条非空真值查询）；
- 3 字符及以上的中文查询最快（**0.09 ms** @20 万条）；
- 不足 3 字符时回退 `LIKE`，代价与纯 `LIKE` 方案相同（20 万条约 **34 ms**），完全可接受；
- 索引体积 **2.72–2.86×** 原文，对个人应用可接受。

**必须同时明确的两点：**
1. **FTS5 默认分词器（`unicode61`）对本项目不可用**：中文召回率实测 **0%**（1–3 字查询）。
   任何"用 FTS5 默认配置做中文搜索"的方案都是无效的。
2. 上述延迟是**桌面 Windows** 的测量值。Android 设备（尤其低端机）预计慢 **2–5 倍**，
   移动端需要实测确认。**在移动端实测前，不得宣称"中文搜索已可用"。**

## 2. 存储与索引构建成本

| 方案 | 库体积 @5万 | 相对基线 | 构建耗时 @5万 | 库体积 @20万 | 相对基线 | 构建耗时 @20万 |
| --- | --- | --- | --- | --- | --- | --- |
| `LIKE`（无索引） | 13.1 MB | 1.00× | 0 ms | 52.7 MB | 1.00× | 0 ms |
| `unicode61` | 17.2 MB | 1.31× | 121 ms | 69.3 MB | 1.31× | 555 ms |
| **`trigram`** | **37.4 MB** | **2.86×** | **447 ms** | **143.2 MB** | **2.72×** | **2124 ms** |
| `bigram`（自研切分） | 67.0 MB | 5.12× | 762 ms | 262.7 MB | 4.98× | 3342 ms |

**解读**：
- `trigram` 的索引约等于原文的 1.7 倍净增（总库 2.7×）。20 万条记录约 **90 MB 索引**——
  对个人应用可接受，但**必须纳入备份体积与移动端存储的考量**。
- 构建耗时随规模近似线性（5万→20万：447→2124 ms，约 4.7×，接近 4× 的记录数增长）。
  对"一次性重建索引"完全可接受。
- `bigram` 体积接近 `trigram` 的两倍（自研 token 表 + 原表），性价比不如 `trigram`。

**关键观察**：
- `unicode61` 的召回率**随数据量增大而下降**（15.2% → 13.2%），因为中文整句被当作单 token，

- `trigram` 与 `bigram` 都达到 100%。`trigram` 的优势在于**不需要自研切分逻辑**。

## 5. 按查询长度的延迟（推荐方案的成本结构）

| 方案 | 1 字 | 2 字 | 3 字 | 4 字 | 6 字 | 英文词 |
| --- | --- | --- | --- | --- | --- | --- |
| **@5 万条** | | | | | | |
| `LIKE` | 9.06 ms | 8.87 ms | 7.91 ms | 7.89 ms | 7.84 ms | 9.93 ms |
| `unicode61` | 0.01 ms | 0.01 ms | 0.01 ms | 0.01 ms | 0.01 ms | 0.87 ms |
| **`trigram`** | **9.04 ms** | **8.84 ms** | **0.03 ms** | **0.02 ms** | **0.03 ms** | **1.54 ms** |
| `bigram` | 3.23 ms | 2.73 ms | 0.34 ms | 0.42 ms | 0.55 ms | 2.21 ms |
| **@20 万条** | | | | | | |
| `LIKE` | 38.1 ms | 34.0 ms | 32.9 ms | 33.0 ms | 32.6 ms | 41.3 ms |
| `unicode61` | 0.01 ms | 0.01 ms | 0.01 ms | 0.01 ms | 0.01 ms | 3.16 ms |
| **`trigram`** | **38.3 ms** | **34.1 ms** | **0.09 ms** | **0.04 ms** | **0.04 ms** | **6.14 ms** |
| `bigram` | 17.1 ms | 0.94 ms | 0.82 ms | 0.92 ms | 1.31 ms | 13.9 ms |

**这张表解释了推荐方案的取舍**：
- `trigram` 在 1–2 字时**与 `LIKE` 完全相同的延迟**——因为 `trigram` 要求 ≥3 字符，
  实现里这两档回退到 `LIKE`。**这不是缺陷，是刻意设计**：短查询用 `LIKE` 已经够快，
  而 `trigram` 对短串本来也无法建立有效索引。
- 3 字以上，`trigram` 比 `LIKE` 快 **350–800 倍**（0.09 ms vs 32.9 ms @20万）。
- 英文查询 `trigram` 比 `LIKE` 快约 7 倍，但比 `unicode61` 慢约 2 倍。
  英文不是主要场景，这个差距可接受。

### 短查询的规模风险

`LIKE` 回退是**全表扫描**，随记录数线性增长：

| 记录数 | 2 字中文查询（`LIKE` 回退） |
| --- | --- |
| 5 万 | 8.84 ms |
| 20 万 | 34.1 ms |
| 50 万（外推） | 约 85 ms |
| 100 万（外推） | 约 170 ms |

**个人生活记录到 20 万条属于重度长期使用**，35 ms 完全可接受。
外推值**未实测**，标注为推断。若将来真的突破 50 万条，需要为高频短词加缓存
或考虑 `bigram`（短查询 0.94 ms，代价是 5× 索引体积）。

## 6. 为什么 `unicode61` 不行（机制说明）

FTS5 的 `unicode61` 按 Unicode 词边界切分，**中文没有空格**，
因此 `检查网格生成失败` 会被切成**一个 token**。查询 `网格` 找的是另一个 token，
永远匹配不到。

实测失败案例（20 万条）：

| 查询 | 长度 | 真值条数 | `unicode61` 找到 |
| --- | --- | --- | --- |
| `字段` | 2 | 5966 | **0** |
| `查询` | 2 | 6043 | **0** |
| `顺` | 1 | 5282 | **0** |
| `服` | 1 | 6076 | **0** |
| `测试编` | 3 | 99 | **0** |

`unicode61` 的英文表现正常（93.9% 召回，未达 100% 是因为抽样查询可能是词的一部分，
如 `inspect` 在 `inspecting` 中）。**结论：必须替换分词方案，或明确放弃中文全文搜索。**

## 7. 候选方案对比与推荐

| 方案 | 召回 | 3+ 字延迟 | 1–2 字延迟 | 索引体积 | 实现复杂度 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| `unicode61` | **0%**（中文） | — | — | 1.31× | 最低 | ❌ **不可用** |
| **`trigram` + `LIKE` 回退** | **100%** | **0.09 ms** | 34 ms | 2.72× | **低**（内置分词器，无自研代码） | ✅ **推荐** |
| `bigram`（自研切分） | 100% | 0.82 ms | **0.94 ms** | **4.98×** | 高（需自研切分 + 维护 token 表 + 索引重建逻辑） | ⚠️ 备选：仅当日志量 > 50 万且短查询成为瓶颈 |
| 纯 `LIKE` | 100% | 33 ms | 34 ms | 1.00× | 最低 | ⚠️ 可行但 3+ 字查询慢 350× |

### 推荐实现

```sql
-- 外部内容表，索引可随时重建（规格 §9.11）
CREATE VIRTUAL TABLE search_fts USING fts5(
  title, body,
  content='record',           -- 外部内容表：索引与原文分离
  content_rowid='id',
  tokenize='trigram'
);
```

查询路由（`domain/rules/search_query.dart`，纯逻辑、可单测）：

```
若 查询串字符数 >= 3  → FTS5 MATCH（trigram）
否则                  → LIKE '%q%'（转义 % _ \）
所有路径统一返回同一 SearchHit 类型（规格 §5 结果对象一致的要求）
```

**必须遵守的约束**：
1. 索引用外部内容表，**可整表重建**，且不是权威数据（规格 §9.11）。
2. `%`/`_`/`\` 在 `LIKE` 回退路径中必须转义（用 `ESCAPE`），
   否则含这些字符的查询会返回错误结果——这是基准脚本里实际处理的问题。
3. 搜索结果必须与筛选（类型/日期/标签/项目/状态）组合，且结果对象类型一致。
4. 短查询没有索引加速，**必须在已知限制中写明**。

## 8. 未验证与限制（不得声称"中文搜索已可用"）

| 未验证项 | 说明 |
| --- | --- |
| **Android 真机性能** | 本基准是桌面 Windows。移动端预计慢 2–5 倍，**必须实测**。20 万条 × 34 ms 桌面值，移动端可能到 100–170 ms |
| 50 万条以上规模 | 表中"外推"值未经实测 |
| 真实语料质量 | 语料是合成的模板句，真实日记的用词分布、长度、标点更复杂 |
| 索引重建在真实库上的耗时 | 基准测的是纯插入后重建；真实库有并发写入与事务 |
| 与结构化筛选组合后的性能 | 基准只测了单表全文查询 |
| 备份体积影响 | 索引 2.72× 会显著增加备份大小，需要纳入 `backup-restore.md` 的容量提示 |
| 排序/相关性 | 基准只测召回与延迟，**未测** FTS5 的 BM25 排序在中文上的合理性 |
| 前缀/模糊匹配 | 未测；`trigram` 支持子串但不支持拼写容错 |

**因此当前状态：方案已选定并给出实测依据，但"中文搜索可用"这一结论只能在
Android 真机实测通过后给出。** 在此之前，`known-limitations.md` 保留相关条目。

## 10. 复现说明

```bash
# 默认 5 万条、120 条查询
node tools/fts5-cjk-bench.mjs

# 大规格
node tools/fts5-cjk-bench.mjs --rows 200000 --queries 120

# 固定种子，结果可复现
node tools/fts5-cjk-bench.mjs --rows 50000 --queries 120 --seed 20261012
```

脚本会打印上述所有表格，并把机器可读结果写入临时目录的 `results.json`。
脚本同时输出"最差召回案例"清单与语料自检信息（零真值查询数、平均匹配条数），
用于判断基准本身是否有效——这一步不可省略，第一版基准正是因为未检查零真值查询
而虚高了 13 条查询的召回率。
