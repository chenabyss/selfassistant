# risks.md — 数据丢失、重复写入、并发修改、迁移与恢复风险分析

这是规格 §13.5 要求的风险分析。每个风险给出：**后果 → 触发条件 → 检测手段 → 缓解措施 → 残余风险**。

风险等级：**R1 = 可能造成不可逆数据丢失**，**R2 = 数据不正确但可修复**，**R3 = 体验/可信度问题**。

**当前规模：61 项（R1 28 / R2 30 / R3 3）。**
其中 §1–§6 为首次设计（47 项），§6.1 为设计复审修订轮新增（14 项，编号 `RV-*`）。
数量由 `tools/count-risks.mjs` 从本文件推导并断言，避免手工维护出错。

---

## 1. 数据丢失风险

### DL-1 用云盘同步 SQLite 文件（R1）

- **后果**：数据库或 WAL 撕裂，产生无法恢复的损坏；两个设备互相覆盖。
- **触发**：用户把 app 数据目录放进 OneDrive/Dropbox/坚果云；或实现者"图省事"直接同步 `.db`。
- **检测**：`quick_check` 报错；`-wal` 与 `.db` 不匹配；数据"回到过去"。
- **缓解**：
  1. 架构上禁止：同步只搬运 `op`，本地库是唯一写入目标（规格 §8.2 明令）。
  2. 启动时检测数据目录是否位于已知云盘同步路径（Windows 下可检查路径/重解析点），
     命中则**警告**用户。
  3. `manifest.sqlite_version` + 启动自检。
- **残余**：用户仍可能手动复制文件。文档与 UI 明确"不要用云盘同步数据目录，请用同步功能或备份"。

### DL-2 迁移失败损坏数据库（R1）

- **后果**：应用无法打开库，用户数据全部不可达。
- **触发**：迁移脚本有 bug；迁移中途断电；迁移过程中被杀死。
- **检测**：迁移前快照 + 迁移后断言（行数、关联数、关键字段）。
- **缓解**：
  1. 迁移前自动 `VACUUM INTO pre_migration_v<N>_<ts>.db` 并**验证**，才允许迁移。
  2. 迁移在**单事务**内执行；失败自动回滚。
  3. 迁移脚本**逐版本手写**，不用自动生成（可审查）。
  4. 每个迁移都有专门的升级测试（用真实旧版数据库文件，见 `testing.md` T-MIG-*）。
  5. 迁移在应用启动的**早期**执行，完成前不启动 UI 与同步（避免半迁移状态被读取）。
- **残余**：磁盘在迁移过程中物理损坏（概率极低，由备份覆盖）。

### DL-3 恢复覆盖唯一可用数据（R1）

- **后果**：旧备份覆盖新数据，且没有退路。
- **触发**：就地恢复；校验失败仍继续；交换时只移动 `.db` 不带 `-wal`。
- **检测**：恢复流程的五个阶段都有明确的前置校验。
- **缓解**：`backup-restore.md` §4 的五阶段流程；关键不变量是
  "任何失败路径都不修改现场" + "交换前一定存在 preRestore" + "整体移动 `-wal`/`-shm`"。
  测试 T-BAK-RESTORE-FAIL-ROLLBACK 与 T-BAK-TRUNCATED 强制守护。
- **残余**：用户在确认对话框上误点确认（缓解：默认按钮是取消；显示"将替换哪段时间的数据"摘要）。

### DL-4 快速记录未持久化（R1，直接违反 §6.1）

- **后果**：用户以为记下了，实际丢了。这是最伤害信任的失败。
- **触发**：写入在 UI 层异步未 await；数据库未就绪时提交；写失败但仍显示成功。
- **检测**：注入写失败的测试；进程被杀测试。
- **缓解**：
  1. 提交路径 = 单事务（`op` + 物化 + outbox），事务成功才显示"已保存"。
  2. 未落库前输入内容保留在输入框，并有本地草稿兜底（进程被杀后可恢复）。
  3. 明确区分"已保存到本机"与"已同步"两种状态文案。
  4. **禁止**先显示成功再异步写。
- **残余**：设备存储满（缓解：写入前检查空间，失败给明确原因）。

### DL-5 删除语义混淆导致误删（R2）

- **后果**：删除项目级联删掉其任务/日志/时间记录（规格 §4.4/§5 明令禁止）。
- **触发**：外键 `ON DELETE CASCADE` 跨对象类型使用；实现者顺手加了级联。
- **检测**：T-INT-PROJECT-DELETE-KEEPS-HISTORY。
- **缓解**：`data-model.md` §6 明确 `ON DELETE CASCADE` **只**用于 `entity`→自身元数据表；
  跨对象引用一律用 `set_element`（无 FK 级联）。所有删除走软删除 + 墓碑。
- **残余**：硬删除（180 天后）会清掉回收站内容（已明确告知用户保留期）。

### DL-6 附件丢失/孤儿化（R2）

- **后果**：引用还在，文件没了；或文件还在，无人引用占用空间。
- **触发**：用户移动/删除源文件；清理任务误删仍在使用的 blob；多设备只有部分有 blob。
- **检测**：`blob.state` + 定期哈希抽检。
- **缓解**：
  1. 导入附件时**复制**进内容寻址目录（不引用原路径），避免外部移动影响。
  2. 删除引用只解引用，blob 由孤儿清理处理，孤儿判定基于**全表引用扫描**，保留 30 天。
  3. 缺失时显示 `missing` 占位，**不**静默删除引用（规格 §4.9）。
  4. 备份默认包含附件并记录 `blobs_pending`。
- **残余**：外部 URL 失效（显示 `reachable=0`，不是数据丢失）。

### DL-7 搜索索引被当作唯一数据源（R2）

- **后果**：索引损坏/未建时"数据不见了"。
- **缓解**：规格 §9.11 明确索引可重建；`architecture.md` 把 `search_fts` 标为**非权威**；
  启动时校验索引行数与实体数，不一致则后台重建。测试 T-SEARCH-REBUILD。

## 2. 重复写入风险

### DW-1 重复推送产生重复对象（R1，违反 §8.3）

- **后果**：一次记录变成两条；统计翻倍。
- **触发**：网络超时后重试（客户端不知道服务端是否已写入）；用户重复点击"转为任务"。
- **检测**：原型测试 1/2/12/15（重推、重复应用、重复删除、部分失败重试）。
- **缓解**：
  1. **客户端生成 `op_id`（UUIDv7）**，服务端 `UNIQUE(op_id)` + `INSERT OR IGNORE` → 幂等。
  2. 出站队列只有收到 ack 才删除；部分失败整批重试（安全，因为幂等）。
  3. **转换去重**（§6.3）：转换前先查 `set_element(field='conversion_refs')`，
     已存在则返回既有对象。UI 按钮在请求进行中禁用。
  4. 应用远端 op 时以 `op_id` 判重（已应用则 no-op）。
- **残余**：用户在两台设备上**手动**各创建一条"同一个任务"——这是两个合法对象，
  系统无法也不应自动合并（只能提供"合并重复项"的人工功能，V1 不做）。

### DW-2 双击/重复提交（R2）

- **后果**：同一秒创建两条相同内容。
- **缓解**：UI 层幂等按钮状态 + 用例层"相同内容的最近 N 秒内重复提交"提示（**提示**而非静默阻止）。
  收集箱**故意**不做内容去重——用户可能真想记两条一样的内容。

### DW-3 重复附件上传（R3）

- **缓解**：内容寻址（sha256），相同内容只存一份、只传一次。原型测试 20 覆盖。

### DW-4 计数类字段跨设备求和导致重复计数（R2）

- **后果**：跨设备同步两轮后数字翻倍。
- **缓解**：**设计上禁止** additive 合并策略；`data-model.md` §5 明确没有任何字段使用求和合并；
  所有总量都是查询派生值。

## 3. 并发修改风险

### CC-1 行级 LWW 静默丢弃并发修改（R1，违反 §8.3）

- **后果**：设备 A 改了标题、设备 B 改了截止时间，合并后一个消失。
- **触发**：按整行 `updated_at` 覆盖。
- **检测**：原型测试 3（不同字段并发编辑双方都要保留）。
- **缓解**：**字段级**版本向量（`field_register`）+ 每字段独立 LWW。这是核心设计决策。
- **残余**：同一字段的真并发只能取一个（`lww`）或保留两版（`text`），无法两者兼得。

### CC-2 文本冲突静默丢一段话（R1，违反 §8.3）

- **检测**：原型测试 5/6。
- **缓解**：`text` 策略 = 当前值 LWW + 落败值写入 `conflict` 表 + UI 横幅。
  **不做**三方合并（长文本自动合并不可靠，会产出用户没写过的句子）。
- **残余**：用户可能忽略冲突提示（缓解：冲突项计入"待处理"，并在对象详情持续显示标记，
  直到用户显式处理）。

### CC-3 因果误判（把"已看到对方修改后的编辑"当成冲突）（R2）

- **后果**：大量虚假冲突提示，用户被噪声淹没而开始忽略真正的冲突。
- **缓解**：版本向量而非纯 HLC；原型测试 6 专门守护"因果更晚的编辑不报冲突"。

### CC-4 冲突记录本身不收敛（R2）

- **后果**：两台设备显示的冲突列表不同，用户困惑。
- **触发**：以"观察时刻"为键记录冲突（原型首次运行实际踩到）。
- **缓解**：以 `losing_op_id` 为唯一键；原型测试 5 断言两侧记录一致。

### CC-5 集合元素被"复活"（R2）

- **后果**：删掉的标签／解除的关系重新出现。
- **缓解**：集合元素带逐元素墓碑（`present=0`），删除也参与总序。
  原型测试 9/10 守护"并发删除不复活"与"真正重新添加生效"。

### CC-6 时钟偏移导致错误胜者（R2）

- **后果**：时钟慢的设备永远覆盖不了；时钟快的设备永久压过所有人。
- **缓解**：
  1. HLC（本设备单调 + 因果一致）。
  2. 远端物理时间超过 `本地墙钟 + 1h` 时**截断**并报警，防止未来时钟把全局时间推走。
  3. 比较顺序 `p → l → d → value_hash → op_id`，保证确定性。
  4. 原型测试 16/17 覆盖。
- **残余**：时钟**慢**的设备其修改在总序中靠前（可能落败）。这是可接受的：
  落败值仍在 op 日志与冲突记录中可见，不会静默消失。

### CC-7 数据库并发访问（`database is locked`）（R2）

- **后果**：写入失败，用户看到错误。
- **触发**：UI isolate 与同步 isolate、后台提醒任务同时写；未开 WAL。
- **缓解**：
  1. 启动时 `PRAGMA journal_mode=WAL`（一人写、多人读）。
  2. drift `NativeDatabase.createInBackground` + 单一写 isolate；多读 isolate 用 `readPool`。
  3. application 层 `WriteQueue` 串行化写入。
  4. `PRAGMA busy_timeout=5000`。
  5. 每个连接都设 `PRAGMA foreign_keys=ON`（**每个连接**，不是一次全局）。
- **残余**：极端争用下仍可能超时（显示可重试错误，不丢数据）。

### CC-8 多设备同时计时（R3，非缺陷）

- **说明**：两台设备各自 running 是**合法**的，不是冲突。
- **缓解**：`timer_state='running'` 的唯一约束是**每设备局部**的；
  同步合并**绝不**自动结束对方的计时器（那会伪造结束时间，违反 §4.5）。

## 4. 数据库迁移风险

| ID | 风险 | 等级 | 缓解 |
| --- | --- | --- | --- |
| MG-1 | 迁移中途失败留下半迁移状态 | R1 | 单事务迁移；失败自动回滚；迁移前快照 |
| MG-2 | 迁移丢失关联数据（外键被重建导致引用断开） | R1 | 每个迁移脚本必须断言"关联数量不减少"；用真实旧库文件测试 |
| MG-3 | 迁移改变 `STRICT` 表约束导致历史脏数据被拒 | R2 | 迁移时先清洗再收紧约束；清洗规则写进迁移注释与测试 |
| MG-4 | 迁移与代码版本不匹配（旧代码打开新库） | R1 | 打开库时检查 `user_version`：库版本 > 代码版本 → **拒绝启动**并明确提示升级应用，绝不写入 |
| MG-5 | 迁移被并发的同步/后台任务打断 | R1 | 迁移在启动早期、UI 与同步启动之前完成；迁移期间持有应用级独占锁 |
| MG-6 | 时区/时间语义在迁移中被改写 | R2 | 迁移**只做结构变更**，不改写已有时间值；历史时间不可变（§6.4） |
| MG-7 | FTS 索引与数据不同步 | R3 | 结构性迁移后标记索引"需重建"，后台重建；索引非权威 |
| MG-8 | 迁移测试只测"能跑通"不测"数据还对" | R1 | 迁移测试必须做**前后行数与字段值比对**，不仅是无异常 |

### 迁移安全规则（写入代码规范）

1. **只前进不后退**：没有 down migration；回退靠迁移前快照。
2. **一次一个版本**：`v7ToV8`、`v8ToV9`…；跨版本升级顺序执行全部步骤，每步独立测试。
3. **禁用破坏性 DDL** 除非有对应的数据搬运步骤与断言。
4. **禁用**在迁移中调用业务逻辑（业务逻辑会随版本变化，历史迁移必须"冻结"）。
5. 每个迁移必须有一条"用真实旧版数据库文件"的集成测试（fixture 进仓库）。

## 5. 备份与恢复风险

| ID | 风险 | 等级 | 缓解 |
| --- | --- | --- | --- |
| BR-1 | 备份是"看起来成功但不可恢复"的 | R1 | §8.4 明确要求实际恢复测试；T-BAK-ROUNDTRIP 用空库真实恢复并逐表比对 |
| BR-2 | 备份期间并发写入 → 快照不一致或损坏 | R1 | `VACUUM INTO`（事务性一致性快照）；测试 T-BAK-CONSISTENT-SNAPSHOT |
| BR-3 | 归档被截断/损坏却仍被恢复 | R1 | `SHA256SUMS` 逐文件校验 + `quick_check` + `foreign_key_check` + 行数比对 |
| BR-4 | 恢复后忘记重建派生数据（FTS、计数） | R2 | 恢复流程显式重建 FTS 并重算派生视图；恢复后跑应用层自检查询 |
| BR-5 | 用户以为"有同步就不用备份" | R2 | UI 分别显示"上次同步"与"上次备份"；首次使用引导说明差异；§8.3 要求二者分开 |
| BR-6 | 加密备份忘记口令 → 备份等于没有 | R2 | 默认不加密；启用时强提示"无法找回"；提供恢复码（可选，明示风险） |
| BR-7 | Windows 上"自动备份"从未发生（应用未启动） | R2 | 明确写进 `known-limitations.md`；启动时检测并提示 |
| BR-8 | 备份文件本身随设备一起丢失 | R1 | 引导用户把备份放到设备之外（外部盘/用户自选目录）；不强制云 |
| BR-9 | 还原了错误时间点的备份，覆盖更新的数据 | R1 | 恢复前显示备份时间与内容摘要，要求显式确认；保留 preRestore 7 天可回退 |
| BR-10 | 附件未包含但用户以为包含 | R2 | `manifest.includes.attachments` + UI 明确显示 `blobs_pending` 数量 |

## 6.1 设计复审修订轮新增风险（RV-*）

这些风险是**修复评审第 1 项（冲突可见性）过程中发现并修复的真实缺陷**。
它们被登记为独立编号，因为它们的性质不同于原有类别：**它们是"并发逻辑实现错误"这一类风险**，
而这类错误的共同特征是**看起来正常工作**。

| ID | 风险 | 等级 | 说明、缓解与守护测试 |
| --- | --- | --- | --- |

### 7.3 一个重要的观察

修订轮新增的 14 项风险中，**9 项来自"修复一个缺陷时发现的其他缺陷"**。
这说明并发相关的设计缺陷具有**聚集性**：一个错误往往意味着同一区域的判断依据也错了。

因此：
- 阶段 9 的 33 条契约测试是**准入条件，不是可选项**；
- 并发相关代码的修改必须同时新增或更新测试；
- 不得因为"测试都过了"就认为并发逻辑已经正确——原型的故事正好相反：
  测试通过之后，才发现原来的测试**没有覆盖**真正的问题（`lww` 冲突可见性）。

**发布门槛（对应规格 §10.4 "不存在已知的高严重度数据丢失、重复写入或同步覆盖缺陷"）**：
所有 R1 风险必须有**自动化测试**覆盖其缓解措施，且测试在两个真实平台（Windows、Android）上通过。
任何未覆盖的 R1 项必须在 `known-limitations.md` 中列为已知缺陷，**不得**宣称 V1 可交付。
