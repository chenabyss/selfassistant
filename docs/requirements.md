# requirements.md — 个人生活信息系统 V1 可测试需求

本文件把 `personal_life_system_v1_spec.md` 转写为**可测试**的需求，并登记其中的**矛盾与缺漏**。
规格是产品基准；本文件只做澄清、编号和判定条件补充，不静默改变产品边界。

- 需求编号：`R-<域>-<序号>`
- 每条需求都有"判定条件"，测试用例必须能直接映射到编号（见 `testing.md`）。
- `[规格 §x]` 指向原规格章节。标 `⚠GAP-xx` 的条目来自缺口登记表，**需要用户确认后才能实现**。

---

## 0. 范围与优先级

| 级别 | 含义 |
| --- | --- |
| P0 | V1 发布的必要条件；缺失即不可交付 |
| P1 | V1 应包含；有明确降级策略可接受 |
| P2 | 明确排除在 V1 之外（登记原因） |

### 0.1 V1 包含（P0/P1）[规格 §2.1]

快速记录收集箱、长期任务、临时事项/提醒、项目、标签、时间记录、工作日志、日记、
显式关联、附件/外部链接基础能力、今日视图、每日回顾、任务与项目详情聚合、
全局搜索与筛选、本地持久化、Windows + Android 客户端、备份/导出/恢复、
多设备同步、自动化测试与迁移测试。

### 0.2 V1 排除（P2）[规格 §2.2]

财务（独立应用，Beancount）、通用数据库构建器、完整知识图谱、
AI 自动生成结论或自动修改正式记录、复杂习惯/目标管理、团队协作与多人权限、
插件市场、任何"必须联网才能记录"的核心能力。

> P2 不是"以后再说"，而是"V1 不得因实现方便而顺手做进来"。
> 例如：**不得**为了做标签而引入"用户自定义实体类型"；**不得**引入通用关系编辑器。

## 1. 通用数据规则

- **R-DATA-01** 所有正式对象具有稳定、不可变的唯一 ID；标题/日期/正文**不得**用作身份。[§4]
  - 判定：修改对象标题后，所有引用仍然指向同一对象；ID 不随任何字段变化。
- **R-DATA-02** ID 全局唯一且离线可生成：UUIDv7（74 bit 随机），不依赖中心分配。
  - 判定：两台离线设备各生成 10 万个 ID，集合无交集（见 `testing.md` T-UNIT-ID）。
- **R-DATA-03** 记录至少含 `created_at`、`updated_at`；有实际发生时间的另存 `occurred_at` 或区间。[§4]
- **R-DATA-04** 时间戳以 UTC 存储（epoch 毫秒）；**另存 IANA 时区 ID**，展示时用设备本地时区。[§4, §4.5]
  - 判定：设备时区改变后，历史记录的"发生时间"不变，只改变本地展示。
- **R-DATA-05** 删除、归档、完成、取消语义互不相同，不互相隐含。[§9.5]
- **R-DATA-06** 聚合视图只读取关联对象，不复制正式数据。[§9.4, §6.6]
- **R-DATA-07** 关联解除不删除两端对象。[§5, §9.6]
- **R-DATA-08** 被引用对象被删除后，引用方显示明确的"已删除/缺失"状态，不得静默指向他物。[§5]
- **R-DATA-09** 重要状态变化可追溯。[§9.8]
  - 判定：任务状态变更、收集记录转换/撤销、删除操作均有可查询的历史条目。

## 2. InboxItem — 快速记录 [§4.1]

- **R-INBOX-01** 提交即持久化，**不得**先要求选择类型。[§4.1, §6.1]
  - 判定：杀进程后重启，记录仍在；断开网络仍成功。
- **R-INBOX-02** 保存失败时保留用户输入并明确提示。[§6.1]
  - 判定：注入数据库写失败，输入不清空，界面出现错误态与重试入口。
- **R-INBOX-03** `status` ∈ {inbox, deferred, processed, archived, deleted}，五个状态语义独立。
- **R-INBOX-04** `processed` 仅表示已整理，原记录不被删除，仍可检索。[§4.1]
- **R-INBOX-05** 由收集记录转换出的正式对象保留来源关系（双向可追溯）。[§4.1]
- **R-INBOX-06** 转换可撤销；撤销**不得**误删已独立编辑过的正式对象。[§4.1]
  - 判定：转换后编辑正式对象，再撤销转换 → 正式对象仍存在，界面提示"来源关系已解除"。
- **R-INBOX-07** 未处理记录不得因跨日而自动完成或删除。[§4.1]
- **R-INBOX-08** 归档与删除必须区分。[§4.1]
- **R-INBOX-09** 重复触发同一转换不得产生重复正式对象。[§6.3]
  - 判定：连点两次"转为任务"，只创建一个 Task，第二次返回既有对象。

## 3. Task — 长期任务 [§4.2]

- **R-TASK-01** `scheduled_date`（计划执行日）与 `due_at`（截止时刻）是不同字段，不互相推导。
- **R-TASK-02** 无项目的任务是合法的。[§4.2]
- **R-TASK-03** 子任务层级有限；创建/修改父任务时防止循环。[§4.2]
  - 判定：构造 A→B→A 的父子链被拒绝，返回明确错误。
- **R-TASK-04** 任务完成**不**自动创建时间记录。[§4.2]
- **R-TASK-05** 任务完成后仍可查看其相关日志与时间记录。[§4.2]
- **R-TASK-06** 状态变化可恢复，至少保留最近一次状态与完成时间。
- **R-TASK-07** `status` ∈ {todo, in_progress, done, cancelled}。

## 4. ReminderItem — 临时事项 / 提醒 [§4.3]

- **R-REM-01** 不要求项目、优先级、子任务或详细描述。[§4.3]
- **R-REM-02** `remind_at`（提醒）与 `due_at`（到期）分开。
- **R-REM-03** 提醒是对象的**属性**，不得建模为一条独立的重复待办。[§4.3]
- **R-REM-04（修订轮强化）** 提醒状态必须区分并**分别呈现**五类情形，不得用单一布尔值概括：

  | 情形 | `notification_state` | 界面必须说明 |
  | --- | --- | --- |
  | 已保存但尚未安排 | `none` | 「已保存提醒（尚未安排）」 |
  | 已成功安排 | `scheduled` | 「已安排提醒」 |
  | 通知权限被拒绝 | `denied` | **「提醒未生效：通知权限被拒绝」** + 前往设置入口 |
  | 系统限制导致无法保证投递 | `failed` | **「提醒可能不会响」** + 具体原因（精确闹钟不可用 / 平台不支持） |
  | 已过期或需重新安排 | `fired` / 待重排 | 「已于 <时间> 提醒」或「需要重新安排」 |

  - 判定：五条路径各有独立状态值与 UI 文案；在拒绝通知权限的设备上创建提醒后，
    **不得**出现「已安排提醒」文案。[§4.3、`platform-toolchain-plan.md` §1.2]
- **R-REM-05** 完成后不再触发该事项的提醒。[§10.3 旅程 B]
- **R-REM-06** V1 不要求复杂重复规则；若支持重复，必须有明确的生成与取消规则。[§4.3]
  - 决策：**V1 不支持重复提醒**（见 `decisions/0006-notifications-and-platform-limits.md`）。
    Windows 不支持重复通知（`periodicallyShow` 抛 `UnsupportedError`），为保持两端行为一致而不实现。
- **R-REM-07（修订轮新增）** 应用**每次启动必须执行"补课"**：
  呈现已过期的提醒、重新安排未来提醒、复查权限并把失效的置为 `failed`。
  - 判定：杀进程 → 跨过提醒时间 → 重新启动 → 该提醒被本机呈现且状态不再是 `scheduled`；
    Android 上重启设备后未来提醒被重新安排。
    [`platform-toolchain-plan.md` §2.1、ADR-0006]
- **R-REM-08（修订轮新增）** Windows 未打包形态下，当能力查询返回"不可取消"时，
  界面**不得**显示"撤回提醒"入口（不得做出平台做不到的承诺）。
  - 判定：能力查询 `canCancel == false` 时该入口不存在。
    [`platform-toolchain-plan.md` §1.1、§3.1]

## 5. Project — 项目 [§4.4]

- **R-PROJ-01** 项目只做聚合，不复制任务/日志/时间记录。[§4.4]
- **R-PROJ-02** 项目可以没有任务或日志。
- **R-PROJ-03** 归档项目不删除其关联对象。[§4.4]
- **R-PROJ-04** 项目 `status` ∈ {active, paused, completed, archived}。

## 6. TimeEntry — 时间记录 [§4.5, §6.4]

- **R-TIME-01** 支持手动补录、修改、删除。
- **R-TIME-02** `end_at` 必须晚于 `start_at`；数据库层 CHECK 约束保护。[§8.2]
- **R-TIME-03** 运行中的计时器以明确的 running 状态表示，**不得**伪造结束时间。[§4.5]
- **R-TIME-04** 应用重启后计时器状态可恢复。[§6.4, 旅程 D]
  - 判定：开始计时 → 杀进程 → 重启 → 计时器仍在运行且已用时长正确（基于 `start_at`，不基于内存计数）。
- **R-TIME-05** 设备时间变化或跨时区后**不得**静默重写历史时间。[§6.4]
  - 判定：把系统时区从 UTC+8 改为 UTC-5，历史 `start_at` 的 UTC 值不变。
- **R-TIME-06** 统计必须区分"原始记录时长"与"去重后覆盖时长"，或在检测到重叠时提示用户。[§4.5]
  - 判定：两条重叠 30 分钟的记录 → 原始 2h，覆盖 1.5h，两者都可见且标注含义。
- **R-TIME-07** 未记录时间不等于漏记时间。[§4.5]
- **R-TIME-08** 任务/项目删除或归档时，历史时间记录不得无提示丢失。[§4.5]

## 7. LogEntry / JournalEntry / Conclusion

- **R-LOG-01** 日志不要求关联项目或任务。[§4.6]
- **R-LOG-02** 日志可关联多个任务、项目、结论与附件。[§4.6]
- **R-LOG-03** 日志正文与任务描述不得自动互相覆盖。[§4.6]
- **R-JRN-01** 日记以日期为主要组织方式，允许自由叙述，不强迫结构化拆分。[§4.7]
- **R-JRN-02** 同一天允许多篇日记（决策；原规格"默认允许多篇"）。[§4.7]
- **R-JRN-03** 日记可引用任务/项目/日志/时间记录；引用不等于复制正文。[§4.7]
- **R-CON-01** 结论必须能追溯到来源记录。[§4.10]
- **R-CON-02** V1 不自动把普通日志推断为正式结论。[§4.10]
- **R-CON-03** 专业知识库由 Obsidian 负责，本应用只保存轻量结论。[§4.10]
- **R-CON-04** 结论/决策在 V1 实现为**记录类型**，不引入通用模板引擎。[§4.10, §2.2]

## 8. Tag [§4.8]

- **R-TAG-01** 标签用于主题/属性，不代替项目与对象关系。[§4.8]
- **R-TAG-02** 标签名称去重规则在实现前固定：**Unicode NFC 规范化 → 去首尾空白 → 折叠内部连续空白 → casefold 比较**；存储保留用户原始大小写。[§4.8 ⚠GAP-13]
  - 判定：`" 工作 "`、`"工作"`、`"ＷＯＲＫ"`→`"work"` 各自按规则判定是否视为同名。
- **R-TAG-03** 删除标签不删除被标记的对象；标签的删除是"标签实体归档 + 解除全部标记"两步语义（见 `data-model.md`）。

## 9. Attachment / ExternalReference [§4.9]

- **R-ATT-01** V1 至少支持外部 URL。[§4.9]
- **R-ATT-02** 本地附件纳入 V1；内容寻址存储（sha256），同内容只存一份。[§4.9 ⚠GAP-24]
- **R-ATT-03** 附件可被多个对象引用；删除引用不默认删除共享附件。[§4.9]
- **R-ATT-04** 备份必须说明附件是否包含在内；界面与文档都要标明。[§4.9, §8.4]
- **R-ATT-05** 文件移动或丢失时显示失效状态，不得静默删除引用。[§4.9]
- **R-ATT-06** 附件本体不进操作日志，只同步元数据与哈希；缺失的 blob 由需要它的设备按需拉取（见 `sync-protocol.md`）。

## 10. 关系模型 [§5]

- **R-REL-01** 关系通过稳定 ID 保存；建立/解除都不删除对象。[§5]
- **R-REL-02** V1 只实现规格列举的明确关系，不做通用关系编辑器。[§5, §2.2]
- **R-REL-03** 多值关系（LogEntry→多任务、JournalEntry→多引用、Conclusion→多来源）用集合语义实现，与 `data-model.md` 的 `relation` 表一致。[§4.6, §4.7, §4.10 ⚠GAP-08/09/10]
- **R-REL-04** 关系的并发修改按集合语义合并（并集 + 逐元素墓碑），不整表覆盖。[§8.3]

## 11. 关键用户流程

- **R-FLOW-01** 快速捕获：任意主页面可发起；提交即成功或明确失败。[§6.1]
- **R-FLOW-02** 每日回顾展示全部 `inbox` + 已到期的 `deferred`。[§6.2]
- **R-FLOW-03** 回顾支持逐条与批量处理；操作为：转任务 / 转临时事项 / 转日志 / 加入日记 / 补录时间记录 / 关联现有对象 / 归档 / 删除 / 稍后处理。[§6.2]
- **R-FLOW-04** 回顾可随时结束，未处理记录保留。[§6.2]
- **R-FLOW-05** 关闭回顾页面**不得**自动把全部标记为完成。[§6.2]
- **R-FLOW-06** 临时事项可升级为长期任务，保留可追溯转换记录。[§6.3]
- **R-FLOW-07** 转换失败时不得删除源对象。[§6.3]
- **R-FLOW-08** 搜索至少支持：全文关键词、类型筛选、日期范围、标签、项目、任务状态。[§6.5]
- **R-FLOW-09** 搜索结果点击进入正式对象详情，而非副本。[§6.5]
- **R-FLOW-10** 项目详情聚合：基本信息、未完成/已完成任务、时间记录与统计、工作日志、日记引用、结论与附件。[§6.6]

## 12. 界面与交互 [§7]

- **R-UX-01** 主要操作少步骤完成。
- **R-UX-02** Windows 支持键盘操作与快捷键；Android 支持触屏快速录入。
  - 判定：Windows 上 `Ctrl+N` 全局唤起快速记录；全流程可纯键盘完成。
- **R-UX-03** 长表单渐进式填写：常用字段先显示，次要字段折叠。
- **R-UX-04** 所有删除操作有确认或撤销机制。
- **R-UX-05** 空状态解释如何开始，而不是只显示空白。
- **R-UX-06** 加载、保存、同步、冲突、权限失败都有可理解的状态提示。
- **R-UX-07** 不得以动画或装饰性统计妨碍快速记录。
- **R-UX-08** 未处理记录数量不得作为羞辱性指标；允许推迟与归档。[§7]

## 13. 技术边界

- **R-TECH-01** 跨平台客户端（Flutter 为首选候选，须先做最小技术验证）。[§8.1]
- **R-TECH-02** 本地关系型数据库 SQLite；schema 变化全部通过版本化迁移。[§8.2]
- **R-TECH-03** **不得**通过通用云盘同步正在使用的 SQLite 文件。[§8.2, §12]
- **R-TECH-04** 数据库升级失败时必须保留可恢复的旧数据或备份。[§8.2]
- **R-TECH-05** 适合原子化的读写使用事务；约束尽量保护 ID 唯一性、外键完整性、时间区间有效性。[§8.2]
- **R-TECH-06** 每台设备有稳定设备 ID。[§8.3]
- **R-TECH-07** 变更有稳定 ID、对象 ID、版本/时间信息、操作类型。[§8.3]
- **R-TECH-08** 支持创建、更新、删除/墓碑。[§8.3]
- **R-TECH-09** 网络中断后可重试；重复发送不得重复创建（幂等）。[§8.3, §9.7]
- **R-TECH-10** 删除必须通过可同步的墓碑或等效机制表达。[§8.3]
- **R-TECH-11** 同一对象并发修改不得静默丢弃一方修改。[§8.3]
- **R-TECH-12** 文本冲突保留冲突版本或提供明确合并界面。[§8.3]
- **R-TECH-13** 任务状态、时间记录、标签、关系都需要**明确**的冲突策略。[§8.3]
- **R-TECH-14** 同步成功 ≠ 备份成功，二者分开设计。[§8.3, §8.4]
- **R-TECH-15** V1 必须能离线使用，网络恢复后继续同步。[§8.3]
- **R-TECH-16** 手动备份。[§8.4]
- **R-TECH-17** 可配置的自动备份，或明确说明 V1 的限制。[§8.4]
- **R-TECH-18** 备份含数据库与必要附件，或明确标示不含的内容。[§8.4]
- **R-TECH-19** 备份文件包含版本信息。[§8.4]
- **R-TECH-20** 恢复前检查版本兼容性与完整性。[§8.4]
- **R-TECH-21** 恢复失败不得覆盖唯一可用的数据。[§8.4]
- **R-TECH-22** 必须执行**实际恢复测试**，而不只测备份文件能否生成。[§8.4]
- **R-TECH-23** 导出提供可读格式（CSV/JSON）；富文本、附件、关系的完整导出需明确限制。[§8.4]
- **R-TECH-24** 默认本地优先；不上传内容用于分析。[§8.5]
- **R-TECH-25** 日志不得记录日记正文、敏感附件内容。[§8.5]
- **R-TECH-26** 同步传输使用安全连接。[§8.5]
- **R-TECH-27** 如采用云同步，明确服务端保存的数据、加密方式与账户恢复方式。[§8.5]
- **R-TECH-28** 不把"本地优先"宣传成绝对安全或自动加密。[§8.5]
- **R-TECH-29** 备份、导出、删除应有清楚的用户控制。[§8.5]
- **R-TECH-30** 搜索索引可重建，不作为唯一数据源。[§9.11]
- **R-TECH-31** 任何导入/同步失败都必须可见并可重试。[§9.12]

### 13.1 设计复审修订轮新增的技术需求

- **R-TECH-34（新增）** Android 产物必须满足 **16 KB 页对齐**要求（Google Play 硬性要求）。

- **R-TECH-35（新增）** 冲突必须对用户可见、可解决，且解决动作作为普通写入同步。

- **R-TECH-36（新增）** 数据库打开路径必须集中在一处，且备份/恢复/迁移**不得假设库是明文的**，

  - 判定：代码审查 + 架构测试（加密开关只影响一个模块）；

### 16.1 已由用户确认的决策（记录备查，不再是待决问题）

| # | 决策 | 落地文档 |
| --- | --- | --- |
| Q1 | **V1 交付可用的多设备同步**（多设备数据协同是产品需求，不降级为未来功能） | `relay-deployment.md` |
| Q2 | **优先自建 HTTPS relay**，并明确部署、费用、维护与隐私边界 | `relay-deployment.md` |
| Q3 | 墓碑保留最小必要信息并长期保留；**操作日志压缩前必须验证恢复与重新同步机制** | `data-model.md` §7、`relay-deployment.md` §6.3 |
| Q7 | 暂以 **Android 10+** 为候选默认值（需核对实际设备） | `platform-toolchain-plan.md` §4.2 |
| Q10 | 尽可能支持应用关闭后的提醒，但**必须分别在 Windows 与 Android 上实测真实行为** | `platform-toolchain-plan.md` §1–§2 |
| Q11 | 接受保留**最小必要元数据**的墓碑，但须有隐私说明 | `data-model.md` §7、`privacy-encryption.md` |
| Q12 | V1 **仅用应用私有目录** + 备份/导出，不支持自定义数据目录 | `known-limitations.md` |
| Q4a | **备份加密默认关闭**；可提供用户主动开启的口令加密，并明确告知忘记口令的后果 | `privacy-encryption.md` §3 |
| Q4b | **本地库采用 L0，默认不加密**；V1 不引入加密引擎，但连接/迁移/备份/恢复/清单必须预留接口 | `privacy-encryption.md` §4.5 |
| Q4c | **V1 不做端到端加密**；启用同步时明确告知 relay 服务端可读正文与附件；**不得宣传 E2E** | `privacy-encryption.md` §8 |
| Q9a | **接受**字段级版本向量 + 操作日志 + 并发冲突可见 + 冲突解决机制 | ADR-0003、ADR-0010 |
| Q9b | **不放弃**字段级并发保留（不允许为简化算法重新引入静默覆盖不同字段） | `sync-options.md` |
| Q9c | **接受** `audit_log` 懒生成（先证明可完整重建，再移除重复写入） | `sync-options.md` §1.1、`data-model.md` §1.1 |
| Q9d | **采用显式同步解决记录**（保证 `keep_winner` 也能在其他设备关闭冲突） | ADR-0010、`sync-protocol.md` §4.1 |
| Q13 | **接受服务端操作日志永久保留**；若将来归档/截断，必须先实现安全的 `resync_required`，且绝不因重同步清空本地库 | `relay-deployment.md` §6.3–6.4 |
| Q14 | **接受**：Android 真机实测通过前，不得宣称中文搜索在移动端可用 | `search-cjk-results.md` §8 |
| Q6 | **先验证 MSIX，再决定 Windows 最终发行形式**；必须先验证打包/未打包的数据目录、迁移与提醒行为 | `platform-toolchain-plan.md` §3.4（M9 为前置） |
| Q8 | **优先建立 GitHub Actions CI**，同时保留真实平台验证任务；CI 成功 ≠ 真机验证通过 | `.github/workflows/ci.yml`、`platform-verification-checklist.md` |

### 16.3 修订轮问题的决策记录（**已全部决定**）

修订轮提出的问题已由用户批准，**不再是待决项**。下表保留原始取舍说明备查。

| # | 原问题 | **决定** | 取舍要点 |
| --- | --- | --- | --- |
| **Q4a** | 备份加密默认值 | **默认关闭**，提供可选口令加密 | 默认关闭优先"一定能恢复"；默认开启优先"泄露防护"，代价是忘记口令=永久丢失 |
| **Q4b** | 本地库加密级别 | **L0 不加密 + 预留接口** | L2 与"低记录成本"冲突；L1 防护有限且必须提供导出恢复密钥 |
| **Q4c** | 是否接受不做 E2E | **接受**，并如实披露服务端可读 | 若必须 E2E → 需要独立设计阶段 + 明文导出逃生通道 |
| **Q4d** | 将来 E2E 的形态 | **延后**（V1 不做） | 影响实现成本与泄露面 |
| **Q4e** | 加密引擎的许可与 OpenSSL 依赖 | **延后**（V1 不引入引擎） | 到真正启用加密时再决 |
| **Q9a** | 是否接受字段级方案 + S1/S2/S3 削减 | **接受**（S1/S2 已实现；S3 暂缓） | 冻结同步协议的前置条件，已满足 |
| **Q9b** | 是否放弃字段级并发保留 | **不接受** | 唯一能显著简化算法的取舍，代价是静默丢字段修改 |
| **Q9c** | `audit_log` 是否懒生成 | **接受**（先证明可完整重建） | 减少约 20–25% 写入行；历史改为投影 |
| **Q9d** | `keep_winner` 行为 | **采用显式同步解决记录** | 保证其他设备也能得知冲突已解决 |
| **Q13** | 服务端 op 日志保留 | **永久保留** | 决定长期离线设备能否安全追赶（⚠GAP-37） |
| **Q14** | 中文搜索宣称口径 | **接受**（真机实测前不得宣称移动端可用） | 避免虚假完成声明 |
| **Q6（更新）** | Windows 发行形态 | **先验证 MSIX 再决定** | MSIX 解决通知取消与枚举，但可能改变数据目录，须先做 M9 |
| **Q8（更新）** | 工具链落地 | **优先 GitHub Actions CI + 保留真机验证任务** | CI 成功不等于真机验证通过 |

> Q15（代码托管）已确认使用 GitHub；Q16（Android 真机）用户确认有真机、待提供型号与版本；
> Q17（Windows 测试机 MSIX 权限）仍未确认。三者是**外部条件**，不是设计分歧，
> 见 §16.2。
