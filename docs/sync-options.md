# sync-options.md — 自建同步方案的必要复杂度评估

> 评审第 2 项要求："比较当前字段级版本向量 + HLC + op-log 方案与更简单的多设备版本控制、
> 冲突检测方案。比较实际实现工作量、离线并发行为、数据丢失风险、服务端要求、
> 测试成本和长期维护成本。不要因为原型的测试通过就直接认定方案已完整验证。"
>
> **本文件不以"原型测试全部通过"作为论据。** 原型目前 33/33，但评审说得对：
> 测试通过只证明**已写的断言**成立，不能证明协议在真实多设备、断网、崩溃、升级场景下正确。
> 下面把"已验证 / 未验证"分开列（§7），并把复杂度逐项标价。

---

## 1. 先说结论

**推荐：保留字段级合并与 op 日志，但砍掉三处非必要复杂度。**
不推荐退回"整行版本号 LWW"，因为那会重新引入评审第 1 项刚修好的缺陷——
同一对象不同字段的并发修改会被静默丢弃。也不推荐买现成引擎（理由见 §6）。

具体建议：

| # | 保留 | 理由 |
| --- | --- | --- |
| 1 | `op` 追加日志 | 同时承担同步、审计、撤销、迁移校验；替代方案要额外造一套变更捕获 |
| 2 | **字段级**版本向量 | 这是"并发不静默丢改"的唯一实现方式；行级版本号做不到 |
| 3 | HLC | 代码量约 60 行（`src/hlc.js` 实测 2.8 KB），解决时钟偏移；替代品（纯墙钟）已被证明不安全 |
| 4 | `text` 与 `set` 两种策略 | 它们解决的是**不同**问题：文本要保留两版，集合要并集。合并成一种会丢信息 |
| 5 | 永久墓碑 | 体积极小（约 100 字节/条），是防止旧设备复活已删数据的必要条件 |

**不建议削减**：版本向量、HLC、墓碑、三种策略。它们各自封堵一个已识别的 R1 风险。

### 削减项的采纳状态（用户已批准，见 §1.1）

| # | 削减 | 状态 | 理由 |
| --- | --- | --- | --- |
| **S1** | 关闭冲突的"派生"机制 → 改为**显式同步解决记录** | ✅ **已采纳并实现** | 原派生判据导致 `keep_winner` 在其他设备上仍显示待处理。改为 `op_type='resolve_conflict'` 的显式 op：幂等、可重放、跨设备收敛 |
| **S2** | `audit_log` 改为**懒生成**（可重建） | ✅ **已采纳并实现** | 它是可重建的历史视图，不应成为第二套权威数据。**先证明了可完整重建**，再移除写入路径中的重复持久化 |
| **S3** | 折叠 `field_register` 逐字段行 | ⏸ **暂缓** | 决策要求先保留正确的字段级语义，用 10 万条实测后**只有指标显示必要时**才改；任何折叠都必须证明重放一致 |

**关键原则**：S3 暂缓是有意的——为省少量存储而重新引入并发语义缺陷，
是比"写放大"严重得多的错误。**先正确，再优化。**

> S1/S2 的实现在 `prototype/sync-core/`：S1 见 `test/conflict.test.js` 的
> `keep_winner emits ONLY a resolution op`、`keep_winner resolution propagates and
> closes the conflict everywhere`、`resolution op is idempotent under repeated
> delivery and reordering`；S2 见 `test/audit.test.js`（7 条，证明历史可完整重建）。

## 2. 四个候选方案

| 方案 | 数据单位 | 并发判定 | 并发策略 | 服务端 |
| --- | --- | --- | --- | --- |
| **A. 当前方案** | 字段级 op | 每字段版本向量 + HLC | 冲突表（所有策略）+ 集合并集 | 极简：`UNIQUE(op_id)` + 单调 `seq` |
| **B. 行级版本号 LWW** | 整行（`updated_at` + `device_id`） | 行级最后写入者胜 | 无（落败整行丢弃） | 极简 |
| **C. 行级版本号 + 字段级冲突检测** | 整行 | 行级 LWW 选胜者，但比较字段差异并记录冲突 | 冲突表 | 极简 |
| **D. 现成引擎**（PowerSync / Couchbase Lite） | 引擎自有 | 引擎自有 | 引擎自有或自写 | 需要真实服务端 |

### 方案 B 为什么被否决（这是最重要的一条）

行级 LWW 无法满足规格 §8.3 的"不得静默丢弃一方修改"。具体反例：

> 设备 A 改 `task.title`，设备 B 改 `task.due_at`，两边都没看到对方的修改。
> 行级 LWW 会整行取一边，**另一个字段的修改永久丢失**。

这不是理论问题——它正是评审第 1 项指出问题的更严重版本。
方案 C 试图打补丁（行级选胜者 + 记录差异），但差异比较需要知道"每个字段最后一次写入是谁"，
否则无法区分"B 没改这个字段"和"B 把它改成了相同的值"——
**最终还是会退化成需要逐字段元数据**，也就是方案 A。

### 方案 D 为什么被否决

评估过 PowerSync、Couchbase Lite、Turso/libSQL、ElectricSQL、Realm、WatermelonDB、
ObjectBox、Ditto（详见 `dart-verification.md` §5）。否决要点：

- PowerSync：服务端权威，简单后端即"逐字段 LWW"——**冲突语义仍要自己写**，
  却要多维护一个服务端 + 上游数据库（Postgres/MySQL/Mongo）+ FSL 许可。
- Couchbase Lite：包自述"非官方产品"，需 Sync Gateway 4，企业版 P2P/加密付费。
- Turso/libSQL：单主页面复制，**没有合并**，官方警告"同步中打开本地库会损坏"。
- Realm：已停止服务。WatermelonDB：仅 React Native。ElectricSQL：无可用 Dart 客户端。
- ObjectBox Sync / Ditto：商业授权；Ditto 的平台文档自相矛盾。

**共同问题**：没有一家提供"任务状态 / 时间区间 / 标签集合各自的冲突策略"这种细粒度控制，
而这正是规格 §8.3 明确要求的。买来的引擎最终仍需在其上再写一层冲突逻辑。

## 3. 实现工作量实测（不是估算）

用原型代码量作为**核心逻辑**的下界（不含 SQLite 持久化、UI、网络、测试）。
下表由 `Get-Content | Measure-Object -Line` 实测（修订轮结束时）：

| 模块 | 文件 | 行数 | 字节 | 说明 |
| --- | --- | --- | --- | --- |
| HLC | `src/hlc.js` | 76 | 2.8 KB | 时钟推进、偏移钳制 |
| 版本向量 | `src/vvec.js` | 56 | 1.9 KB | 比较、合并、递增 |
| 合并策略 | `src/merge.js` | 172 | 7.4 KB | 三策略判定、总序、快照 |
| 事件存储 | `src/store.js` | 525 | 23.6 KB | 应用、冲突、集合、游标、时钟 |
| 字段模式 | `src/schema.js` | 122 | 3.8 KB | 声明式策略表 |
| 哈希/UUID | `src/hash.js` | 50 | 2.3 KB | UUIDv7、稳定序列化、相等 |
| **核心合计** | | **1001** | **41.8 KB** | |
| 参考 relay | `src/relay.js` | 75 | 3.1 KB | 服务端逻辑（幂等 + 游标） |
| 测试 | `test/*.js` | 791 | 38.4 KB | 33 条契约测试（含 harness） |

**解读**：核心合并/同步逻辑约 **1000 行 JavaScript**（不含测试容器与参考 relay）。
移植到 Dart 后因类型标注、空安全与显式模型类会更多，估 **1400–1800 行**。
参考 relay 约 75 行（生产版本不含认证/TLS/部署，见 `relay-deployment.md`）。

作为对比，方案 B（行级 LWW）的核心逻辑约 **200–300 行**——
即当前方案多出约 **3–5 倍核心代码**，但换来"并发不丢改"。
方案 C 介于两者之间（约 500–700 行），但存在 §2 指出的退化风险。

**这些数字只覆盖核心算法。** 真正的工作量在别处，见 §4。

## 4. 真正的成本在哪里（评审要求"比较实际实现工作量"）

### 4.1 工作量分布（我的估计，标注依据）

| 工作项 | 相对工作量 | 依据 |
| --- | --- | --- |
| 核心合并算法 | 1×（约 900 行，见 §3） | 实测代码量 |
| 持久化到 SQLite（表、索引、事务、迁移） | 2–3× | `data-model.md` 有 8 张同步相关表 + 手写迁移 |
| 同步循环 + 网络 + 重试 + 错误可见性 | 1–2× | `sync-protocol.md` §6、§10 |
| **测试** | **3–5×** | 33 条契约测试要移植；另加 L2/L3/L5 各层 |
| relay 服务端 + 部署 | 2–4× | 见 `relay-deployment.md`（含认证/TLS/备份/版本兼容） |
| 长期维护（协议演进、兼容性、故障排查） | 持续 | 不可量化，但不为零 |

**结论：核心算法只占总量约 10%。** 削减算法复杂度（方案 B）省下的是那 10% 的一小部分，
却会牺牲功能正确性。**真正的成本在测试、持久化和服务端**——无论选哪个方案都跑不掉。

### 4.2 写放大实测（方案 A 的主要代价）

字段级版本向量意味着每次字段写入产生多行。按 `architecture.md` §5.1 的唯一写入路径：

| 一次字段写入产生的行 | 表 | 是否可省 |
| --- | --- | --- |
| 1 | `op` | 不可省（同步与审计的载体） |
| 1 | 物化业务表（UPDATE，不增行） | — |
| 1 | `field_register`（UPSERT，不增行） | 可评估（建议 S3） |
| 1 | `sync_outbox` | 不可省（未推送队列） |
| 1 | `audit_log` | **可省**（可重建，建议 S2） |

即每次字段写入约 **3 行新增**（op + outbox + audit）加 2 次 UPSERT。
去掉 `audit_log` 后约 **2 行**。

对照方案 B：每次**行**写入约 1 行（变更日志）+ 1 次 UPDATE。
但方案 B 的"一次用户编辑"可能覆盖多个字段，实际差异小于表面倍数。

**这项需要用真实数据测**（`testing.md` T-LOAD-100K），当前**未测**。

### 4.3 测试成本（最大的隐形成本）

| 层次 | 方案 A 需要 | 方案 B 需要 |
| --- | --- | --- |
| 合并语义契约 | 33 条（已写成） | 约 8–10 条 |
| 属性测试（交换律/幂等/崩溃） | 必须（随机交错已证明能抓 bug） | 简化 |
| 迁移测试 | 8 张表 × 版本 = 多 | 少 |
| 端到端双设备 | 必须 | 必须 |
| relay 契约测试 | 必须 | 必须 |

方案 A 的测试成本**明显更高**，但注意：原型中 8 个真实缺陷有 **5 个**是被
"随机交错 + 重复投递 + 顺序无关"这类测试抓出来的。
方案 B 省掉这些测试的同时，也省掉了抓 bug 的能力——而它的 bug 表现为**静默丢数据**。

## 5. 风险对照（评审要求"数据丢失风险"）

| 风险 | 方案 A | 方案 B | 方案 C |
| --- | --- | --- | --- |
| 同对象不同字段并发修改 | ✅ 都保留 | ❌ **永久丢失一个字段** | ⚠️ 取决于是否退化为 A |
| 同字段并发修改 | ✅ 可见冲突，可恢复 | ❌ 静默取一方 | ✅ 记录冲突 |
| 文本并发编辑 | ✅ 两版保留 | ❌ 丢一段 | ⚠️ 需另设规则 |
| 集合元素并发增删 | ✅ 并集 + 逐元素墓碑 | ❌ 整集合覆盖 | ⚠️ 需另设规则 |
| 删除 vs 并发编辑 | ✅ 墓碑 + 总序 | ⚠️ 取决于实现 | ⚠️ |
| 时钟偏移 | ✅ HLC + 钳制 | ❌ 墙钟排序，快时钟永久压制 | ⚠️ |
| 重复投递 | ✅ op_id 幂等 | ✅ 需行级幂等键 | ✅ |
| 旧设备复活已删数据 | ✅ 永久墓碑 | ⚠️ 需墓碑 | ⚠️ |
| 实现自身有 bug 的风险 | ⚠️ **更高**（代码多） | ✅ 更低 | ⚠️ 中 |
| 协议升级/兼容 | ⚠️ 需版本协商 | ✅ 简单 | ⚠️ |

**净判断**：方案 A 用"实现更复杂"换取"数据不丢"。
对一个**个人生活记录**应用，用户无法容忍"随手记的东西悄悄少了"，
所以这个交换是划算的。但必须承认：**方案 A 自身出 bug 的概率更高**，
因此 §4.3 的测试投入不是可选项，而是方案 A 成立的前提。

## 6. 服务端要求对照

| 方案 | 服务端要求 |
| --- | --- |
| A / B / C | 极简：一张 `op` 表（`UNIQUE(op_id)` + 单调 `seq`）+ blob 存储。可自建，也可退化为"同步目录"适配器 |
| D | 需要引擎自己的服务端 + 上游数据库（PowerSync）或 Sync Gateway（Couchbase） |

**注意（评审第 4 项）**：即使选 A/B/C，"极简服务端"也**不等于零成本**。
部署、认证、TLS、服务端备份、版本兼容、附件容量、可用性都要做。
详见 `relay-deployment.md`。

## 7. 已验证 vs 未验证（诚实清单）

评审指出"不能因为原型测试通过就认为协议已验证"。逐项列出：

### 已验证（有可执行测试）

- 合并的交换律/幂等性（33 条中的收敛类测试、随机交错测试）
- 幂等：重复推送/重复应用/重复墓碑
- 游标无缺口、崩溃后安全重放
- 部分失败推送的整批重试
- 时钟偏移（慢 1 小时 / 快 48 小时）
- 冲突可见性、去重、顺序无关、解决后收敛
- 集合并集与逐元素墓碑
- 删除不被旧数据复活（**单进程内模拟**）

### 未验证（原型无法覆盖）

| 未验证项 | 为什么原型覆盖不到 | 什么能覆盖 |
| --- | --- | --- |
| 真实网络中断/超时/半开连接 | 内存 relay 无网络 | 阶段 9 的真实 relay + 故障注入 |
| 进程崩溃与断电 | 单进程内存 | 真实设备上的杀进程/断电测试 |
| 真实设备间时钟偏移 | 注入的假时钟 | 真机改系统时间 |
| 数据库持久化与事务 | 内存 Map | Dart + SQLite 集成测试 |
| 升级/协议版本兼容 | 无版本概念 | 版本协商测试 |
| 大数据的性能与体积 | 未测 | T-LOAD-100K |
| 同步服务端并发与一致性 | relay 是单进程内存 | relay 的并发测试 |
| 附件传输 | 只有哈希去重 | 真实 blob 上传下载 |
| `keep_winner` 在其他设备的行为 | 已识别但只在本文件描述 | 端到端双真机验证 |

**因此：当前状态是"协议核心语义已验证，端到端未验证"。**
这与评审的判断一致，也是 `phases.md` P9 设为"双实例真实同步"门槛的原因。

## 8. 推荐与后续

### 推荐

**保留方案 A 的架构，采纳 S1/S2/S3 三处削减，然后按 §7 的未验证清单补齐端到端验证。**

理由汇总：
1. 方案 B 会重新引入刚修好的缺陷，且失败模式是静默丢数据（最糟的一类）。
2. 方案 C 存在向 A 退化的必然性。
3. 方案 D 无法提供规格要求的细粒度冲突策略，且引入服务端/许可依赖。
4. 复杂度确实更高，但实测核心算法只占总量约 10%；真正成本在测试与服务端，任何方案都跑不掉。
5. S1/S2/S3 可在不牺牲正确性的前提下减少实现量与写放大。

### 需要用户决策（更新后的问题清单）

| # | 问题 | 影响 |
| --- | --- | --- |
| Q9a | 是否接受"保留字段级方案 + 采纳 S1/S2/S3 削减"？ | 冻结协议的前置条件 |
| Q9b | 若希望进一步简化：是否接受**放弃"同对象不同字段并发修改都保留"**？ | 这是唯一能显著简化算法的取舍，代价是静默丢字段修改。**我不推荐** |
| Q9c | 是否接受 `audit_log` 改为懒生成（S2）？ | 减少写放大；代价是"历史"查询需要投影计算 |
| Q9d | 是否接受 `keep_winner` 在其他设备保持待处理（当前行为），或改为显式同步解决记录（S1）？ | 影响是否为"解决"再造一张同步表 |

### 建议的验证顺序（在冻结协议之前）

1. **S2 先落地**（去掉 `audit_log` 写放大），再测写放大与体积——这是最便宜的一步。
2. 用 Dart 移植 33 条契约测试（阶段 9 准入条件）。
3. 做 T-LOAD-100K 实测，用真实数据决定 S3 是否需要。
4. 端到端双真机验证 §7 的未验证清单。
5. 全部通过后再冻结协议。
