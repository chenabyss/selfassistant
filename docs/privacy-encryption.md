# privacy-encryption.md — 隐私与加密决策材料

> 评审第 5 项要求："分别分析本地数据库加密、备份加密、传输加密和端到端加密。
> 说明密钥保存、忘记密钥、设备丢失、换机恢复和服务端可见性方面的取舍，并给出推荐方案。"
>
> 评审特别强调：**"不能笼统地用'支持加密'概括"**。本文件因此把四个**互相独立**的问题分开，
> 每个都给出：防住谁 / 防不住谁 / 代价 / 忘记密钥的后果 / 推荐。

---

## 0. 一句话结论

| 层 | 推荐 | 理由 |
| --- | --- | --- |
| **传输加密** | ✅ **必做**（TLS 1.2+，必须校验证书） | 成本近乎为零，防住网络窃听 |
| **备份加密** | ⚠️ **可选，默认关闭** | 关闭时备份是明文，但"备份一定能恢复"优先于保密；提供口令加密并明示无法找回 |
| **本地数据库加密** | ⚠️ **V1 默认关闭，预留开关** | 主要防"设备被拿走"，防不住已解锁的运行中设备；代价是密钥与恢复链复杂度 |
| **端到端加密（服务端不可读）** | ❌ **V1 不做**，V2 候选 | 与"新设备从零恢复"和"服务端可运维"直接冲突，代价远大于收益 |

**最关键的一条澄清**：**HTTPS 不是端到端加密。** 使用自建 relay 时，
服务端**能读到日记正文**（`server_op.value_json` 是明文）。
任何"我们用了加密所以很安全"的说法都必须按本文件的层级拆开讲。

## 1. 先明确威胁模型（否则加密是在防不存在的敌人）

| # | 威胁 | 现实性 | 哪一层能防 |
| --- | --- | --- | --- |
| T1 | 网络路径上的窃听（公共 WiFi、ISP） | 高 | **传输加密** |
| T2 | 备份文件被他人拿到（U 盘丢失、云盘误传、邮件附件） | 中高 | **备份加密** |
| T3 | 设备被他人短暂拿到 / 被盗且**未解锁** | 中 | **本地库加密** + 系统锁屏 |
| T4 | 设备被盗且**已解锁**（或 PIN 很弱） | 中 | ⚠️ 基本防不住（见 §4.3） |
| T5 | relay 服务器被入侵 / 云服务商查看 | 中 | **端到端加密**（V1 不做） |
| T6 | 应用自身日志/崩溃报告泄露正文 | 中 | 应用层脱敏（已有 T-PRIV-NO-CONTENT 测试） |
| T7 | 恶意应用在**同一设备**上读取应用私有目录 | 低-中（未 root） | 仅本地库加密 + 系统沙箱 |
| T8 | 用户自己的误操作（误删、误覆盖） | **高** | **备份 + 墓碑**（不是加密） |

**注意 T8**：对个人生活记录应用，**最可能真实发生的"数据事故"是用户自己误删**，
而不是攻击者。加密对 T8 毫无帮助，备份和墓碑才有用。
这解释了为什么本文件把"备份一定能恢复"排在"备份保密"之前。

**明确不在威胁模型内**：国家级对手、物理取证实验室、供应链攻击（部分由
`package:sqlite3` 的 sha256 + SLSA attestation 覆盖）。

## 2. 传输加密（必做）

| 项 | 决策 |
| --- | --- |
| 最低版本 | TLS 1.2，推荐 1.3 |
| 证书校验 | **必须**；客户端**不得**提供常规的"跳过证书校验"开关 |
| 明文 HTTP | 客户端默认**拒绝** |
| 例外 | 局域网模式（用户显式选择）允许 http，但 UI **必须**标注"未加密传输" |
| 自签证书 | 仅允许用户显式导入信任，并标注风险 |

**防住**：T1。**防不住**：T5（服务端自己能看到明文）。

实施细节见 `relay-deployment.md` §5。

## 3. 备份加密（可选，默认关闭）

这是 ADR-0009 已定的方案，此处补全取舍。

| 项 | 设计 |
| --- | --- |
| 算法 | AES-256-GCM（认证加密，防篡改） |
| 口令派生 | **Argon2id**（内存困难，抗 GPU 暴力） |
| 默认 | **关闭** |
| 清单 | `manifest.json` 保持**明文**（只含元数据，便于恢复前检查版本兼容） |
| 正文与附件 | 加密 |

### 3.1 为什么默认关闭

**核心权衡：备份的首要目标是"能恢复"。**

加密备份引入了一个新的、**不可逆**的失败模式：忘记口令 = 备份等于没有。
而"忘记口令"的概率远高于"备份文件被攻击者拿到"。

具体风险对比：

| 场景 | 不加密备份 | 加密备份 |
| --- | --- | --- |
| 用户忘记口令 | 无影响 | **数据永久不可读**（无后门、无恢复码） |
| 备份文件被他人拿到 | 全部内容泄露 | 安全 |
| 用户需要在 5 年后恢复 | 直接恢复 | 必须还记得口令 |
| 用户需要把备份交给家人保管 | 泄露风险 | 安全 |

**决策**：默认关闭（可恢复性优先），提供开关并**强提示**"忘记口令无法找回"。

### 3.2 可选的缓解：恢复码

提供一个 24 词恢复码（或 32 字节 base32），由用户离线抄写：

- **优点**：忘记口令时仍可恢复。
- **缺点**：用户很可能把恢复码和备份放在一起——那样加密就形同虚设。
- **结论**：作为**可选**功能提供，并在 UI 明确说明"不要和备份放在一起"。

### 3.3 与规格的一致性

规格 §8.5 要求"不把'本地优先'宣传成绝对安全或**自动加密**"。
默认关闭并明示，正是对该条款的遵守。

## 4. 本地数据库加密（V1 默认关闭，预留开关）

### 4.1 技术可行性（已核实）

`package:sqlite3` 3.x 的 build hooks 支持替换加密实现，**无需改代码结构**：

```yaml
# pubspec.yaml
hooks:
  user_defines:
    sqlite3:
      source: sqlite3mc      # SQLite3 Multiple Ciphers；或 sqlcipher
```

- 预编译二进制包含三种：上游 SQLite（默认）、SQLite3MultipleCiphers、SQLCipher。
- Windows / Android 均支持（`dart-verification.md` §3.1）。
- **注意许可**：SQLCipher 构建在 Windows/Linux/Android 上链接 OpenSSL，
  且 SQLite3MultipleCiphers 与 SQLCipher 有各自的许可证（不是公有领域）。
  选用前需确认许可可接受。
- 还可用 `source: source` 自行编译并传入编译选项。

**未验证项**：加密引擎的实际性能开销、与 FTS5 索引的交互、迁移时的重加密流程。
这些需要在工具链就绪后实测（见 `dart-verification.md` §7）。

### 4.2 防住什么 / 防不住什么

| | 说明 |
| --- | --- |
| ✅ 防住 T3 | 设备未解锁时被拿走，数据库文件无法直接读取 |
| ✅ 防住 T7（部分） | 未 root 设备上恶意应用即使读到文件也解不开 |
| ❌ 防不住 T4 | **应用运行中、数据库已解锁时，任何能读进程内存的手段都能拿到数据**；用户解锁了设备就默认解锁了应用 |
| ❌ 防不住 T8 | 误删靠备份，不靠加密 |
| ❌ 防不住 T6 | 日志泄露靠脱敏，不靠数据库加密 |

**必须说清楚**：数据库加密**不是**"设备被偷也安全"。
它只是把攻击门槛从"拷走一个文件"提高到"需要设备解锁后的运行时访问"。

### 4.3 代价（这是 V1 默认关闭的真正原因）

| 代价 | 说明 |
| --- | --- |
| **密钥必须被保存** | 否则每次打开都要输密码 → 与"低记录成本"（核心产品目标）直接冲突 |
| 密钥存在哪 | 若用系统钥匙串（Windows 凭据管理器 / Android Keystore）：**与不加密相比，防护提升有限**——因为钥匙串同样绑定设备解锁状态；若用用户口令派生：**每次启动要输密码**，与产品目标冲突 |
| 忘记密钥 | 全库不可读。且与备份加密叠加时，恢复链是"备份口令 + 数据库密钥"两把 |
| 备份与密钥必须配套 | 备份的是**加密后的**数据库文件；换机恢复需要**同一密钥**。密钥丢失 = 备份也打不开 |
| 迁移复杂度 | 加密库的迁移必须走同一加密连接；`VACUUM INTO` 产物也是加密的；迁移前快照同样加密 |
| 性能 | WAL + 加密可能显著影响写入吞吐（**未实测**） |
| 第三方依赖与许可 | 引入 OpenSSL 链接与额外许可（§4.1） |
| 搜索 | FTS5 索引同样被加密，**但查询过程在内存中解密**，不影响搜索能力；索引体积不受影响 |
| **对开发的影响** | 所有备份/恢复/迁移测试都要在加密配置下再跑一遍，测试矩阵翻倍 |

### 4.4 推荐方案（分层，允许用户选择）

| 级别 | 密钥来源 | 体验 | 防护 |
| --- | --- | --- | --- |
| **L0（默认）** | 不加密 | 零摩擦 | 仅靠系统锁屏 + 应用沙箱 |
| **L1** | 密钥由系统钥匙串保管（`flutter_secure_storage`） | 零摩擦（自动解锁） | 防"设备未解锁时被拿走"；**防不住已解锁设备** |
| **L2** | 密钥由用户口令派生（启动时输入一次/每次） | 有摩擦 | 同上 + 防钥匙串被读；代价是体验 |

**推荐 V1 实现 L0 + 预留切换能力**，并在已知限制中明确写出"当前数据库未加密"。
理由：
1. 核心产品目标是**低记录成本**，L2 与它冲突；L1 的防护提升有限却增加一整条失败链。
2. L0 → L1/L2 的**切换**需要"重写整个库"（不能原地加密），
   但只要**备份/恢复/迁移**在设计上支持加密配置，切换就是可控的一次性操作。
   **因此 V1 的关键要求不是"实现加密"，而是"不要让加密成为将来无法加入的东西"。**

### 4.5 V1 必须为加密预留的东西（否则将来加不进去）

| 要求 | 原因 |
| --- | --- |
| 打开数据库的路径**集中在一处**（`infrastructure/db/connection.dart`） | 加密开关只改这一处 |
| 备份/恢复/迁移**不假设库是明文的** | 对加密库，`VACUUM INTO` 需要正确的 `PRAGMA key` |
| 备份清单记录**是否加密**与**加密引擎** | 换机恢复必须知道用哪个引擎 |
| 密钥与备份**分开存放**的设计 | 避免"密钥跟着备份一起丢" |
| 测试矩阵预留加密配置 | 加密下的备份恢复必须能测 |
| **不在日志里打印密钥或 `PRAGMA key` 语句** | 明显但常被忽略 |

## 5. 端到端加密（V1 不做，V2 候选）

### 5.1 它要解决什么

**T5：服务端（或云服务商）能读你的日记。**

自建 relay 时这一条尤其重要：`server_op.value_json` 是明文，
服务器管理员（也就是用户自己）能看到全部内容；若 relay 被入侵，内容泄露。

### 5.2 为什么 V1 不做

| 冲突 | 说明 |
| --- | --- |
| **与"新设备从零恢复"冲突** | 新设备要解密，必须拿到密钥。若密钥只存在于其他设备上，那就需要一个密钥分发/配对协议（QR 码、短语、设备间信道）；若密钥由用户口令派生，用户又必须记住并输入强口令 |
| **与"忘记密钥"的后果叠加** | 服务端不可读意味着**服务端也帮不了你**——密钥全丢就是永久不可读，没有管理员重置这条路 |
| **与备份恢复链冲突** | 备份若用另一套密钥，就变成两套密钥管理 |
| **与"服务端可运维"冲突** | 服务端无法做任何内容级诊断（如"这条 op 是什么"） |
| 实现成本 | 密钥派生、设备配对、密钥轮换、多设备密钥同步——**这是一个独立的大工程** |
| 与 V1 目标的关系 | 规格 §8.5 只要求"如采用云同步，明确服务端保存的数据、加密方式和账户恢复方式"，**没有要求 E2E** |

### 5.3 若将来要做，最小可行形态

1. **仅加密敏感字段值**（日记/日志正文），元数据（时间、类型、标签）仍明文。
   → 代价：标签与时间仍泄露；但保留了结构化查询与同步的简单性。
2. 密钥 = 用户口令派生（Argon2id）+ 每设备一份密钥封装（key wrapping）。
3. 新设备配对通过**一次性短码 + 已有设备确认**（不依赖服务端）。
4. **必须**同时提供"导出明文备份"的逃生通道——否则忘记口令等于永久失去全部日记，
   这对个人记录应用是不可接受的风险。

### 5.4 重要的表述纪律

- ❌ 不得说"端到端加密" —— V1 没有。
- ❌ 不得说"本地优先所以绝对安全" —— 规格 §8.5 明确禁止。
- ✅ 应说："数据默认只存在你的设备上；启用同步后，你自己的同步服务器能读取内容；
  传输过程加密；数据库默认未加密，因此设备解锁状态等于应用可读状态。"

## 6. 换机恢复：四条路径与它们各自需要什么

这是评审点名要说明的。**换机是新设备从零开始**，因此最能暴露加密设计的破绽。

| 路径 | 需要什么 | 若缺少会怎样 |
| --- | --- | --- |
| **A. 从备份恢复**（推荐主路径） | 备份文件 + （若备份加密）口令 + （若库加密）库密钥 | 备份加密口令丢失 → 备份不可读；库密钥丢失 → 恢复出的库打不开 |
| **B. 从 relay 全量同步** | 设备注册令牌 + （若库加密）库密钥 | E2E 启用时，服务端数据不可读 → 必须从已有设备获取密钥 |
| **C. 设备间直接传输**（局域网/本地） | 两台设备同时在手 | E2E 启用时也需密钥传输通道 |
| **D. 无备份、无 relay、仅旧设备损坏** | **无解** | **数据永久丢失** —— 这正是"同步不等于备份"的原因 |

**结论**：无论选择哪种加密级别，**路径 A（备份）必须始终可用且经过实测**。
`backup-restore.md` §8 的 11 项 T-BAK-* 测试因此不能被加密引入的复杂度绕过——
**加密配置下必须再跑一遍关键几项**。

### 6.1 密钥的存放位置（按加密级别）

| 级别 | 密钥位置 | 换机时如何拿到 |
| --- | --- | --- |
| L0 | 无 | — |
| L1（钥匙串） | 系统钥匙串 | **不一定能随备份迁移**：Windows 凭据管理器 / Android Keystore 的内容通常不随应用数据备份导出 → **换机需重新提供密钥**，因此必须提供"导出密钥"或"从备份口令派生"的路径 |
| L2（口令派生） | 用户记忆 | 用户输入口令 |
| 备份加密 | 用户记忆（或恢复码） | 用户输入口令/恢复码 |

**关键陷阱（必须写进文档）**：L1 用钥匙串保管密钥时，
**系统级备份（如 Android Auto Backup、Windows 文件历史）不会带上钥匙串内容**。
如果密钥只存在钥匙串里，用户换机后会得到"备份在手但打不开"的结果。
因此 **L1 必须同时提供"导出恢复密钥"功能**，并提示用户妥善保存。

## 7. 服务端可见性总表（对用户如实披露）

| 数据 | V1 服务端能看到吗 | 说明 |
| --- | --- | --- |
| 日记/日志正文 | ⚠️ **能**（明文） | `server_op.value_json` |
| 任务标题、状态、时间 | ⚠️ 能 | 同上 |
| 标签、关系 | ⚠️ 能 | 同上 |
| 附件内容 | ⚠️ 能 | blob 明文存储 |
| 设备标识 | 能 | `device_id` + label |
| 用户身份/邮箱 | **不收集** | V1 无账户系统 |
| 使用行为分析 | **不收集** | 规格 §8.5 |
| 服务端访问日志 | 保留 30 天，**不含内容** | 只记请求计数、字节数、错误码、device_id、seq 范围 |

**必须做**：
- UI 在启用同步时明确展示"服务端可读取内容"这一点（一次性确认，不是藏在小字里）。
- 服务端日志**不得**记录 `value_json`（测试 T-RELAY-NO-CONTENT-LOG 守护）。

## 8. 其他隐私要求（规格 §8.5 逐条对照）

| 规格条款 | 状态 | 实现/证据 |
| --- | --- | --- |
| 默认本地优先 | ✅ | 无 relay 时全部功能可用（除跨设备同步） |
| 不上传内容用于分析，除非用户明确启用并知晓范围 | ✅ | 无任何分析上传；无遥测 |
| 日志不得记录日记正文、敏感附件内容 | ✅ | `Logger` 端口脱敏白名单 + 测试 T-PRIV-NO-CONTENT |
| 同步传输使用安全连接 | ✅ | TLS 1.2+（`relay-deployment.md` §5） |
| 如采用云同步，明确服务端保存的数据、加密方式和账户恢复方式 | ⚠️ **部分** | 已明确"保存什么"与"未加密"（§7）；"账户恢复"在 V1 无账户，设备授权吊销见 `relay-deployment.md` §4 |
| 不把"本地优先"宣传成绝对安全或自动加密 | ✅ | 本文件 §5.4 表述纪律；`known-limitations.md` L-28 |
| 备份、导出、删除应有清楚的用户控制 | ✅ | 备份/导出/恢复向导；删除为软删除 + 180 天回收站（ADR-0005） |

## 9. 推荐方案汇总与待决问题

### 9.1 推荐（可直接作为 V1 起点）

| 层 | V1 决策 | 需要用户确认 |
| --- | --- | --- |
| 传输加密 | **必做**：TLS 1.2+，必须校验证书 | 无需确认 |
| 备份加密 | **默认关闭**，提供可选口令加密（AES-256-GCM + Argon2id），可选恢复码 | Q4a |
| 本地库加密 | **默认关闭（L0）**，但**预留 L1/L2 切换能力**（§4.5 的 6 条要求） | Q4b |
| E2E | **V1 不做**，列入 V2 候选；UI 如实披露服务端可读 | Q4c |
| 服务端日志 | 不含内容，保留 30 天 | 无需确认 |

### 9.2 待决问题

| # | 问题 | 选项与代价 |
| --- | --- | --- |
| **Q4a** | 备份加密的默认值？ | (1) 默认关闭（推荐，可恢复性优先）(2) 默认开启（更安全但忘记口令=永久丢失） |
| **Q4b** | 本地数据库加密级别？ | (1) L0 不加密 + 预留开关（推荐）(2) L1 钥匙串（零摩擦，防护有限，**必须提供导出恢复密钥**）(3) L2 口令（防护最好，与"低记录成本"冲突） |
| **Q4c** | 是否接受 V1 不做 E2E，并接受"服务端可读"这一如实披露？ | 若必须 E2E → 需要独立设计阶段，且必须提供明文导出逃生通道 |
| **Q4d** | 若将来做 E2E：是否接受"仅加密正文、元数据仍明文"的最小形态？ | 影响实现成本与泄露面 |
| **Q4e** | 是否接受选用 SQLCipher / SQLite3MultipleCiphers 带来的许可证与 OpenSSL 依赖？ | 若否，则本地库加密只能自己实现或放弃 |

### 9.3 对阶段计划的影响

| 阶段 | 影响 |
| --- | --- |
| P1（骨架） | 数据库打开路径集中一处；备份/迁移不假设明文；日志脱敏（§4.5） |
| P8（备份恢复） | 备份清单记录"是否加密 + 引擎"；加密配置下**必须**跑 T-BAK-ROUNDTRIP 与失败回滚 |
| P0/P10 | 若选 L1/L2，需实测加密引擎的性能与 FTS5 交互（当前未验证） |
