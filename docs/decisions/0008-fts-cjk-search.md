# ADR-0008：中文全文搜索采用 FTS5 `trigram` + 短查询 `LIKE` 回退

- 状态：**已决定**（依据实测数据；移动端性能仍待验证）
- 日期：2026-10-12（修订轮更新：由"待验证"转为"已决定"）
- 关联：规格 §6.5、§9.11；`docs/search-cjk-results.md`；`docs/testing.md` T-INT-SEARCH-REBUILD；`docs/known-limitations.md` L-27

> **本 ADR 已由设计复审修订轮更新。** 原状态为"待验证"，四个候选方案并列。
> 评审第 6 项要求"用至少 5 万条混合中英文测试记录"实测比较。
> 实测已完成（`docs/search-cjk-results.md`），因此本 ADR 现在给出**已决定的方案**。

---

## 1. 背景

规格 §6.5 要求搜索至少支持"全文关键词"。
本项目打包的 SQLite（`package:sqlite3` 3.7.0 内含 **3.53.4**）确定包含 FTS5，
本机实测的 3.53.3 也确认 `fts5`、`tokenize='trigram'`、外部内容表均可用
（`tools/probe-sqlite.mjs`）。

**问题**：FTS5 的默认分词器 `unicode61` 按 Unicode 词边界切分，
而中文没有空格分词，一整句会被当成**单个 token**。
实测结果（20 万条混合中英文语料，`tools/fts5-cjk-bench.mjs`）：

| 查询长度 | `unicode61` 召回率 |
| --- | --- |
| 1–3 字中文 | **0%** |
| 4 字中文 | 2.4% |
| 6 字中文 | 50.0% |
| 英文词 | 93.9% |
| **平均** | **13.2%** |

这不是"效果差"，而是**根本不工作**。因此必须替换分词方案。

---

## 2. 决策

**采用 `trigram` 分词器 + 查询串不足 3 字符时回退 `LIKE` 子串匹配。**

```sql
-- 外部内容表：索引与原文分离，可随时重建（规格 §9.11）
CREATE VIRTUAL TABLE search_fts USING fts5(
  title, body,
  content='record',
  content_rowid='id',
  tokenize='trigram'
);
```

查询路由（`domain/rules/search_query.dart`，纯逻辑、可单测）：

```
若 查询串字符数 >= 3  → FTS5 MATCH（trigram）
否则                  → LIKE '%q%'（必须转义 % _ \ 并使用 ESCAPE）
所有路径统一返回同一 SearchHit 类型（§6.5 要求结果对象一致）
```

---

## 3. 理由（全部有实测数据支撑）

### 3.1 召回率：唯一达到 100% 且实现最简单的方案

| 方案 | 平均召回 | 3 字以上中文延迟（20 万条） | 索引体积 | 实现复杂度 |
| --- | --- | --- | --- | --- |
| `unicode61` | **13.2%** | — | 1.31× | 最低 |
| **`trigram` + `LIKE` 回退** | **100%** | **0.09 ms** | **2.72×** | **低**（内置分词器，无自研代码） |
| 自研 `bigram` | 100% | 0.82 ms | **4.98×** | 高（需自研切分 + 维护 token 表） |
| 纯 `LIKE` | 100% | 32.9 ms | 1.00× | 最低 |

`trigram` 与 `bigram` 都达到全长度 100% 召回，
但 `trigram` **不需要自研切分逻辑**，且索引体积只有 `bigram` 的约 55%。

### 3.2 为什么保留短查询回退而不是让 `trigram` 处理

FTS5 的 `trigram` **要求查询串至少 3 个字符**（少于 3 无法构建三元组索引）。
而中文双字词（"网格"、"日记"）非常常用。因此 1–2 字必须走别的路径。

实测证明这个组合是可行的：`trigram` 在 1–2 字的延迟**与纯 `LIKE` 完全相同**
（20 万条下 34.1 ms vs 34.0 ms）——因为这两档正是回退到 `LIKE`。

**这不是缺陷，是刻意设计**：短查询用 `LIKE` 已经够快，
而 `trigram` 对短串本来也无法建立有效索引。

### 3.3 为什么不用自研 `bigram`

虽然 `bigram` 在短查询上更快（0.94 ms vs 34 ms），但：
- 索引体积接近 `trigram` 的两倍（4.98× vs 2.72×）；
- 需要自研切分逻辑（中英混排、标点、数字的边界处理）并长期维护；
- 需要维护独立的 token 表与重建逻辑，与"索引可重建"（§9.11）的简单性相冲突。

**结论**：仅当日志量突破 50 万且短查询成为实际瓶颈时，才考虑切换到 `bigram`。

### 3.4 为什么不用纯 `LIKE`

3 字以上查询慢 **350–800 倍**（0.09 ms vs 32.9 ms @20 万）。
虽然短查询延迟相同，但没有理由放弃 3 字以上的巨大收益。

---

## 4. 必须遵守的约束

1. **外部内容表**：`content='record'`，索引**可整表重建**，且不是权威数据（§9.11）。
2. **`LIKE` 回退必须转义** `%`、`_`、`\` 并使用 `ESCAPE`；
   否则含这些字符的查询会返回错误结果（基准脚本中已实际处理）。
3. **结果对象类型一致**：全文与筛选（类型/日期/标签/项目/状态）组合后
   返回同一 `SearchHit` 类型（§6.5）。
4. **短查询无索引加速**，必须写入已知限制。
5. **索引体积**：约原文 1.7 倍净增（总库 2.72×）。20 万条约 90 MB。
   **备份应支持"不含索引、恢复后重建"**，否则备份体积显著增加。

---

## 5. 后果

- **正面**：全长度 100% 召回；3 字以上极快；零自研自然语言处理代码；行为可预测。
- **负面**：
  - 索引体积 2.72×（**会显著增加备份体积**，L-33）；
  - 1–2 字中文查询是**全表扫描**，随记录数线性增长（20 万条 34 ms；50 万推测约 85 ms）；
  - 未测 BM25 排序在中文上的合理性（只测了召回与延迟）；
  - **移动端性能未验证**（预计慢 2–5 倍）。

## 7. 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| `unicode61`（FTS5 默认） | 中文召回率 0%（1–3 字），不工作 |
| 自研 `bigram` | 索引近 5×，需自研切分并长期维护；仅作备选 |
| 纯 `LIKE` | 3 字以上慢 350–800 倍 |
| 自研 FTS5 C tokenizer | 需编写并编译 C 代码并与 build hooks 集成，显著提高两端构建复杂度与失败风险，与"可复现构建"冲突 |
