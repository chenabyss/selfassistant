# ADR-0003：同步采用自建 op-log + 字段级版本向量（不买现成同步引擎）

- 状态：**已决定**（通道选择仍待用户回答 Q2）
- 日期：2026-10-12
- 关联：规格 §8.3、§9.7；`docs/sync-protocol.md`；`prototype/sync-core/`

## 背景

规格 §8.3 给出一长串硬性要求：设备 ID、变更带 ID/版本/操作类型、创建/更新/墓碑、
重试幂等、删除用墓碑、并发不静默丢改、文本冲突保留、**任务状态/时间记录/标签/关系都要有明确冲突策略**、
同步成功≠备份成功、离线可用。
最后一段还说：若没有合适的同步服务，先定义可替换的 Sync Adapter 接口并完成单设备核心功能。

## 决策

**自建同步协议**：

1. **搬运单位是 `op`（字段级操作）**，不是表行。
2. **每个字段一份版本向量** `{deviceId: counter}`，用于判定 dominates/dominated/concurrent。
3. **HLC（混合逻辑时钟）** 作为总序依据，比较顺序 `p → l → d → value_hash → op_id`。
4. **三种合并策略**（在 `field_schema` 中按实体类型**预先声明**）：
   `lww` / `text`（保留双版本）/ `set`（并集 + 逐元素墓碑）。
5. **无 additive 合并**：任何计数都是查询派生值。
6. **服务端极简**：`UNIQUE(op_id)` + 单调 `seq` + `since/limit` 游标，不合并、不解决冲突。
7. **游标与变更在同一事务提交**（崩溃安全的关键）。
8. **附件内容寻址**（sha256），本体不进 op 日志。
9. **墓碑永久保留**（`entity` 行，约 100 字节）。

## 理由

### 为什么必须字段级

规格 §8.3 明确禁止"同一对象并发修改时静默丢弃一方修改"。
整行 `updated_at` LWW 会丢弃"设备 A 改标题 + 设备 B 改截止时间"中的一个。
字段级版本向量是满足该条款的最小机制。

### 为什么需要版本向量，而不只是 HLC

只用 HLC 会把"B 已经看到 A 的修改后才改的"误判为并发冲突，
产生大量虚假冲突提示，最终让用户忽略真正的冲突（风险 CC-3）。
原型有专门测试守护这一点。

### 为什么不买现成引擎（逐一评估）

| 方案 | Windows 桌面 | 关键否决点 |
| --- | --- | --- |
| PowerSync | ✅ 官方矩阵含 Windows | 服务端权威；简单后端即"逐字段 LWW"，冲突语义要自己写；**服务端为 FSL-1.1-ALv2 许可**（禁止竞争性使用）；必须配 Postgres/MySQL/Mongo |
| Couchbase Lite (`cbl`) | ✅ Windows ≥10 | 官方声明"非官方 Couchbase 产品"；需 Sync Gateway 4；企业版 P2P/加密需付费；v3→v4 单向升级 |
| Turso / libSQL | ✅（社区包） | **页面级单向复制，无合并**；官方警告"同步中打开本地库会导致数据损坏"——直接触碰风险 DL-1 的同类问题 |
| ElectricSQL | ❌ | 无可用 Dart 客户端（0.x 遗留） |
| Realm / Atlas Device Sync | — | 已停止服务 |
| WatermelonDB | ❌ | 仅 React Native |
| ObjectBox Sync | 数据库 ✅ | Sync 需商业授权，内部实现未公开到可评估 |
| Ditto | ⚠️ 文档自相矛盾 | pub.dev 声明支持 Windows，README 写 "Planned"；不实测不采用 |

更关键的是：规格要求的冲突策略**必须由我们定义**（状态怎么合、时间区间怎么合、标签怎么合）。
现成引擎要么不给这个控制（服务端权威），要么要求一整套服务与许可。
而我们要的语义并不大——已用 **20 条可执行测试**证明可实现且正确。

### 为什么"预先声明 field_schema"而不是"首次写入时注册"

这是**原型实测**踩到的缺陷：若允许首次写入注册策略，
那么任何提前触碰该字段的代码路径（例如创建对象时写初始值）会把它**永久钉死在 LWW**，
之后真正的 `text` 声明就会冲突。
因此：启动时按实体类型声明，**未声明字段写入直接抛错**。

### 为什么冲突记录以 `losing_op_id` 为键

同一次冲突会在两台设备上各被观察一次（赢方应用落败 op 时、输方应用获胜 op 时）。
若以"观察时刻"记录，两侧会产生字段互换的两条记录，**冲突列表本身不收敛**。
以落败 op 为键后，两侧推导出的记录完全一致。这也是原型实测到的缺陷。

### 为什么不做 CRDT/OT

文本需求只是"不静默丢一段话"，不是"实时协同编辑"。
引入 Automerge/Yjs 类方案会带来：二进制文档格式（迁移与备份复杂化）、
体积增长、与 SQLite 关系模型的双重真相来源。
"保留两版 + 人工合并"以极小代价满足 §8.3，且与 Automerge 的 loser-preservation 模型同构。

## 后果

- **正面**：完全掌控冲突语义；无插件/无 Rust 构建；无服务依赖即可离线；
  数据不经第三方；协议已由可执行原型验证；Dart 实现有明确的验收清单（20 条测试）。
- **负面**：
  - 需要自建 relay（或退化为文件交换适配器）——取决于 Q2。
  - 协议演进与兼容性由我们负责（需版本协商字段）。
  - 服务端也要做备份（relay 不是备份，§8.3）。
  - **字段级版本向量会增加数据库写入量**（每字段一行 `field_register`），
    在 10 万对象规模下需实测性能（见 `testing.md` T-LOAD-100K）。
- **必须移植的验证**：`prototype/sync-core/test/core.test.js` 的 20 条测试
  逐条移植为 Dart 测试，作为同步模块的准入门槛。

## 开放项

- **Q1**：V1 是否交付**可用**的同步（自建 relay / 局域网 / 文件交换），
  还是只交付 Sync Adapter 接口并明确标注"多设备同步未完成"（规格 §8.3 允许后者）。
- **Q2**：通道选择（HTTP relay / 局域网直连 / 用户自有 WebDAV 或对象存储）。
- 服务端变更日志的保留策略（当前设计：永久，因为 op 是权威历史）。
