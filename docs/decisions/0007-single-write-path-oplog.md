# ADR-0007：写入路径唯一化 —— 操作日志 + 物化状态双结构

- 状态：**已决定**
- 日期：2026-10-12
- 关联：规格 §9.1–§9.12、§8.2、§11 步骤 3；`docs/architecture.md` §5.1；`docs/data-model.md`

## 背景

规格同时要求以下若干条，单独看都合理，合起来则互相制约：

| 条款 | 要求 |
| --- | --- |
| §9.1 | 正式对象使用稳定 ID |
| §9.4 | 聚合视图不复制正式数据 |
| §9.7 | 同步操作具备幂等性 |
| §9.8 | 重要状态变化可追溯 |
| §9.10 | 迁移必须保留已有记录和关联 |
| §8.3 | 并发修改不得静默丢弃一方 |
| §8.2 | 查询和写入必须使用事务处理适合原子化的操作 |

"每个实体一张表、直接 UPDATE 行"的传统做法无法同时满足：
- 无法追溯（UPDATE 覆盖了旧值）；
- 无法做字段级并发控制（没有每字段的版本信息）；
- 无法幂等（行级操作没有天然唯一键来表达"这是同一个变更"）；
- 撤销只能靠额外审计表，而审计表与主表容易不一致。

## 决策

**所有写入都经过一条唯一路径**：

```
UseCase.mutate(entity, field, value)
  └─ BEGIN IMMEDIATE
       ├─ 域规则校验
       ├─ INSERT INTO op(...)                -- 追加，不可变，含 op_id/vv/hlc/strategy
       ├─ UPSERT 物化业务表（task / time_entry / ...）
       ├─ UPSERT field_register(entity_id, field, vv, hlc, op_id)
       └─ INSERT INTO sync_outbox(op_id)     -- 待推送
     COMMIT
```

> **修订（S2，用户已批准）**：写入路径**不再包含 `audit_log` 写入**。
> 历史视图改由 `op` 按需投影（`auditProjection`），因为它本就可重建——
> 在写入时同步落盘属于纯写放大（每次写入多一行，约 20–25%）。
> 采纳前已**先证明历史可完整重建**：
> `prototype/sync-core/test/audit.test.js` 共 7 条测试，覆盖
> create/delete/状态变更/关系变更的捕获、空设备重放一致、跨设备一致、
> 任意重放顺序一致，以及"写入路径中不存在物化审计存储"的守护。
> 因此本 ADR 的"可追溯"要求（§9.8）仍然满足，只是改为派生实现。

**禁止**任何绕过该路径的直接 `UPDATE` / `INSERT`（由 Code Review 与
数据访问层封装保证：物化表只对外暴露只读查询接口）。

**核心不变量**：
> 物化状态永远等于把 `op` 按合并规则重放的结果。

该不变量由测试 `T-DB-REPLAY` 守护（随机生成 op 序列 → 物化状态 vs 重放状态必须全等）。

### 派生数据与权威数据的分级

| 类别 | 表 | 是否权威 | 可否重建 |
| --- | --- | --- | --- |
| 历史/因果 | `op` | ✅ | ❌（唯一历史来源） |
| 当前状态 | 业务表 + `field_register` + `set_element` | ✅ | ✅（由 op 重放） |
| 冲突待办 | `conflict` | ✅ | ⚠️ 部分（可由 op 重放重新推导） |
| 同步状态 | `sync_outbox` / `sync_cursor` | ✅（同步用） | ❌（重建会重发，但幂等所以安全） |
| 全文索引 | `search_fts` | ❌ | ✅ 随时重建（§9.11） |
| 审计视图 | `audit_log` | ❌ | ✅ 由 op 重建 |

## 理由

### 为什么用 op 日志而不是"仅审计表"

若主表直接 UPDATE、审计表另记一份，则：
- 两份数据可能不一致（尤其崩溃时）；
- 同步仍需另一套变更捕获机制（触发器或 CDC），复杂度更高；
- 字段级版本信息仍无处存放。

把 op 作为**一等权威数据**，则同步、审计、撤销、迁移校验全部复用同一份数据。

### 为什么物化状态也要保留（不只在查询时重放）

- 重放全量 op 得到当前状态的性能在长期使用后不可接受。
- 物化状态让查询与索引简单（FTS5 索引的是物化表）。
- 但物化状态是**可重建**的，因此"两者不一致"是可检测、可修复的故障，而非数据丢失。

### 为什么撤销是"写反向 op"而不是"删除 op"

- op 日志不可变才能承担审计与同步的职责。
- 删除历史会导致"离线设备重新推上来"复活被撤销的操作。
- 反向 op 参与版本向量与总序，因此撤销本身也是可同步、可追溯的。

### 为什么不用数据库触发器自动记录 op

- 触发器无法生成 HLC（需要设备时钟与逻辑计数）、无法读取 `field_schema` 的策略、
  无法为集合语义写入 `present` 墓碑。
- 触发器逻辑难以单元测试，且与迁移脚本的交互复杂。
- 显式的用例层写入更容易审查与测试。

## 后果

- **正面**：
  - 一次写入同时满足原子性、可追溯、可同步、可撤销、可测试。
  - `T-DB-REPLAY` 提供了一个强不变量用于检测实现漂移。
  - 迁移可以校验"op 与物化状态仍一致"。
- **负面**：
  - 每次写入产生多行（op + 物化 + field_register + outbox + audit），
    写入放大明显。**需在阶段 1 实测**（见 `testing.md` T-LOAD-100K）；
    若不可接受，优化方向是合并 `audit_log`（它可由 op 重建，可以懒生成）。
  - 数据库体积增长快于传统结构（有 op 日志）。由 90 天压缩策略控制（ADR-0005）。
  - 需要纪律：任何"临时方便"的直接 UPDATE 都会破坏不变量。因此
    `infrastructure/db` 必须只在内部暴露写接口，并加一个静态检查测试
    （禁止在 `packages/infrastructure` 之外出现对业务表的 INSERT/UPDATE SQL）。
