## §13.1 需求理解与范围清单

### 对产品意图的理解

这个应用的核心不是"功能多"，而是**三件事做对**：

1. **记录成本低到不会犹豫**（§6.1 快速捕获、§7 少步骤）——所以快速记录不得强制分类，
   且**提交即持久化**。
2. **数据语义明确到不会自相矛盾**（§4 各规则、§9 一致性）——所以删除/归档/完成/取消四种语义
   必须分开，计划日期与截止日期必须分开，提醒与到期必须分开。
3. **数据可追溯、可恢复、可测试**（§5 关系、§8.4 恢复、§10 测试）——所以需要稳定 ID、
   不复制正文的聚合、墓碑、真实恢复测试。

V1 的闭环（§1）本质是一条链路：**捕获 → 安全暂存 → 整理为正式对象 → 从多个入口调用同一份数据 → 重启/升级/同步后仍一致 → 可备份可恢复**。
任何一个环节"看起来实现了但实际不可靠"，整个产品就失去意义——因为用户把生活记录托付给它。

### 范围清单

**V1 包含（P0/P1）**：快速记录收集箱、长期任务、临时事项/提醒、项目、标签、时间记录、
工作日志、日记、显式关联、附件/外部链接基础能力、今日视图、每日回顾、
任务与项目详情聚合、全局搜索与筛选、本地持久化、Windows + Android 客户端、
备份/导出/恢复、多设备同步、自动化测试与迁移测试。

**V1 排除（P2）**：财务（独立应用，Beancount）、通用数据库/关系构建器、完整知识图谱、
AI 自动生成结论或自动修改正式记录、复杂习惯/目标管理、团队协作与多人权限、
插件市场、任何"必须联网才能记录"的核心能力。

**边界守卫**（明确不做，防止实现时越界）：不做通用关系编辑器（§5）、
不做结论模板引擎（§4.10）、不做重复提醒（§4.3 允许）、
不做 Obsidian 双向同步（§4.10/§12）、不做三方文本合并（本设计决策）。

详见 `requirements.md`（100+ 条编号需求，每条带判定条件）。

## §13.2 技术选型与平台验证计划

### 选型结论

| 项 | 选择 | 关键依据 |
| --- | --- | --- |
| 客户端 | **Flutter**（Windows + Android 单代码库） | 规格 §8.1 首选；官方双端支持；桌面有键盘/窗口能力 |
| 最低版本 | **Flutter 3.38.1**（建议当前稳定 3.47） | 3.38 才在 stable 开放 build hooks/code assets；`flutter_local_notifications` 22.3.2 要求 ≥3.38.1 |
| 数据库 | **SQLite 3.53.4**，经 **`package:sqlite3` 3.7.0** 的 build hooks 打包 | 含 FTS5；两端同一份构建；**已核实版本** |
| 访问层 | **drift 2.35.2** + 手写迁移 | 类型安全；迁移可审查 |
| 同步 | **自建 op-log + 字段级版本向量 + HLC** | 规格要求每类字段都有明确冲突策略；已用可执行原型验证 |
| 通知 | `flutter_local_notifications` 22.3.2，**尽力而为模型** | 平台限制无法消除 |
| 备份 | `VACUUM INTO` + ZIP + 清单 + SHA256 | SQLite 官方认可的一致性快照方式 |

### 三个重要的技术发现

**① `sqlite3_flutter_libs` 已 EOL，必须绕开**

pub.dev 上其最新版为 `0.6.0+eol`，描述直接写着
*"Not used anymore, update to version 3.x of package:sqlite3 instead"*，
且该版本**移除了包内全部代码**。drift ≥2.32 已不再需要它。
→ 决策：不用它，也不用 `drift_flutter`（其依赖链仍指向它）。见 ADR-0002。

**② 打包的 SQLite 版本躲过了一个真实的 WAL 缺陷**

SQLite 的 WAL-reset 缺陷影响 **3.7.0–3.51.2**，在 **3.51.3** 修复，
触发条件是 **≥2 个连接同时写入/检查点**——正是本项目（单写 isolate + 读池 + 后台任务）的形态。
本项目打包 **3.53.4**，已超出。已写入 ADR-0002 作为**禁止降级**约束。

**③ 中文全文搜索不能用默认方案**

FTS5 的默认分词器按 Unicode 词边界切分，**中文整句会变成单个 token**，
"搜索关键词"实际不可用。这不是可以留到后面顺手解决的问题，
必须在阶段 7 之前确定方案（trigram / bigram / LIKE 降级）。见 ADR-0008 与 Q5。

### 平台验证计划（`dart-verification.md` §7 有逐项命令与判据）

V1 环境与构建 → V2 数据库/FTS5/依赖链/16KB 对齐 → V3 通知（两平台，含权限拒绝与撤销）
→ V4 后台行为 → V5 附件导入 → V6 单实例与并发写 → V7 真实备份恢复 → V8 双设备同步 → V9 性能。

### ⚠️ 本次验证的性质（必须说清楚）

**已经在当前构建机上实际执行的**：
- 环境探测：OS 版本、权限、磁盘、工具链、网络边界（[实测]，见 `dart-verification.md` §2）。
- 同步协议核心：零依赖 Node 原型 **33/33 测试通过**，并**发现并修复了 8 个真实设计缺陷**
  （详见 `sync-protocol.md` §9.3）。
- SQLite 能力实测：`tools/probe-sqlite.mjs` 确认本机 SQLite 3.53.3 具备 FTS5（含 trigram）、
  STRICT 表、json1、部分唯一索引，且已超过 WAL-reset 缺陷的修复版本 3.51.3。
- **中文搜索基准实测**：用 5 万与 20 万条混合中英文语料比较 4 种方案
  （见 `search-cjk-results.md`）。这是本轮**唯一能在无 Flutter 工具链下完成的"实测级"验证**。

**仅做了文档核实的**：Flutter/drift/插件的版本与平台支持声明、SQLite 编译选项与版本、
通知在两端的行为限制、后台执行的可行性。这些都标注了来源。

**完全无法执行的**：任何 Flutter 构建与真机运行。原因是本机
**没有 Flutter、没有 MSVC、没有 Android SDK**（且当前无管理员权限）。

> 因此"Windows 与 Android 客户端技术方案验证"目前是**文档级 + 原型级**，
> 不是设备级。我不会把它说成已验证。补齐工具链是**当前唯一的阻塞项**（Q8）。

## §13.4 数据模型草案

采用**操作日志 + 物化状态**双结构（理由见 ADR-0007）。

**通用表**：`entity`（身份/类型/创建更新/软删除/归档/墓碑 HLC）、
`op`（不可变操作日志，含 `op_id`/`vv`/`hlc`/`strategy`）、
`field_register`（每字段版本向量）、`set_element`（集合语义 + 逐元素墓碑）、
`conflict`（以 `losing_op_id` 为唯一键）、`field_schema`（**预声明**合并策略）、
`sync_outbox` / `sync_cursor` / `device` / `blob`。

**业务表**：`inbox_item`、`task`、`reminder`、`project`、`time_entry`、
`log_entry`、`journal_entry`、`conclusion`、`tag`、
`attachment_meta`（内容寻址）+ `external_ref_meta`（**拆成两个实体**）。

**关系的实现原则**：单值关系用列（`task.project_id`、`task.parent_task_id`），
多值关系用 `set_element`。这样同时满足"只实现规格列举的关系"（§5）
与集合语义的并发安全。

**关键字段语义**：
- `task.scheduled_date`（本地日期 `YYYY-MM-DD`）与 `task.due_at`（UTC 瞬时）**分离**（§4.2）。
- `time_entry.start_at/end_at` 存 **UTC 毫秒** + `tz_id`（IANA）；`end_at > start_at` 由 CHECK 约束保证。
- 计时器 = `timer_state='running'` 的一行（`end_at IS NULL`），**落库**，跨重启恢复。
- `reminder.reminder_at` 与 `due_at` 分离；`notification_state` 落库（权限被拒也可见）。
- `tag.name` + `tag.name_key`（NFC → trim → 折叠空白 → casefold）。

**可见性矩阵**：active / archived / deleted（软删 180 天）/ tombstoned 四种状态
在"列表 / 全局搜索 / 聚合视图"三处的可见性已明确定义（解决规格未定义处）。

完整 DDL 与字段合并策略总表见 `data-model.md`。

## §13.5 同步与备份风险分析

### 同步的核心风险与对策

| 风险 | 对策 | 验证 |
| --- | --- | --- |
| 重复推送产生重复对象 | 客户端生成 `op_id`（UUIDv7）+ 服务端 `UNIQUE(op_id)` + 仅 ack 后出队 | 原型测试 1/2/12/15 |
| 行级覆盖静默丢改 | **字段级**版本向量 | 原型测试 3/4 |
| 文本冲突丢一段话 | `text` 策略保留双版本 + UI 处理；**不做**三方合并 | 原型测试 5/6 |
| 集合元素被"复活" | 逐元素墓碑（`present=0`） | 原型测试 9/10 |
| 删除被旧数据复活 | `entity` 墓碑**永久保留** | 原型测试 11/12 |
| 崩溃导致丢数据或重复 | 游标与变更**同一事务**提交 | 原型测试 13/14 |
| 时钟偏移导致错误胜者 | HLC + 未来时间钳制 + `p→l→d→hash→op_id` 总序 | 原型测试 16/17 |
| **同步成功被误当备份成功** | 二者分开设计与显示；同步只保证一致，回滚靠备份 | 文档 + UI |

### 备份的核心风险与对策

| 风险 | 对策 |
| --- | --- |
| 快照不一致（复制使用中的库） | `VACUUM INTO`（事务性一致性快照）；**禁止**直接复制文件（含 `-wal` 也不行） |
| 归档损坏仍被恢复 | `SHA256SUMS` + `quick_check` + **`foreign_key_check`**（`integrity_check` **不查外键**）+ 行数比对 |
| 恢复覆盖唯一可用数据 | **五阶段恢复**：任何失败路径都不修改现场；交换前必有 `pre_restore` 快照；`.db` 与 `-wal`/`-shm` **整体**移动 |
| 只测"备份能生成" | 规格 §8.4 硬性要求**实际恢复测试**；`testing.md` 定义了 11 项 T-BAK-* 测试 |
| 迁移失败损坏数据 | 迁移前自动快照 + 单事务 + 逐版本手写 + 真实旧库 fixture 测试 |
| 版本不兼容 | `format_version` 与 `schema_version` 分开检查；更高版本**拒绝**恢复 |

### 完整风险登记

`risks.md` 登记了 **47 项**风险（**20 项 R1** = 可能不可逆丢失，24 项 R2，3 项 R3），
每项给出后果、触发条件、检测手段、缓解措施与残余风险。所有 R1 项在发布前必须有测试覆盖。
（数量由 `tools/count-risks.mjs` 从 `risks.md` 推导并断言，避免手工维护出错。）

### 原型发现的设计缺陷（值得单独指出）

规格要求"编码前先设计同步协议"。我把协议写成**可执行原型**并跑测试，
结果在写代码阶段就发现了 3 个真实缺陷——这些在纯文档评审中不会暴露：

1. **合并策略未持久化** → 重放 op 时丢失 `text` 语义，文本冲突被降级为静默覆盖。
2. **策略"先写后声明"** → 提前写初始值的路径把字段永久钉死在 LWW。
3. **冲突记录以"观察时刻"为键** → 两台设备的冲突列表字段互换、**不收敛**。

三者都已修复并各配有测试。Dart 实现必须移植全部 20 条测试作为阶段 9 的准入门槛。

## §13.6 按垂直切片的开发计划

10 个阶段，详见 `phases.md`（含每阶段的测试与退出标准）。

| 阶段 | 内容 | 依赖 |
| --- | --- | --- |
| **P0** | **工具链与技术验证**（执行 `dart-verification.md` §7） | — |
| P1 | 应用骨架、数据库、**手写迁移框架**、唯一写入路径、错误处理 | P0 |
| P2 | 快速记录与收集箱（**数据丢失风险最高**） | P1 |
| P3 | 长期任务与临时事项/提醒（含通知能力抽象与启动补课） | P2 |
| P4 | 项目、标签与关系（聚合不复制、删除不级联） | P3 |
| P5 | 日记、工作日志、结论（含文本冲突端到端） | P4 |
| P6 | 时间记录与统计（区间约束、计时持久化、重叠统计） | P5 |
| P7 | 搜索、今日视图、每日回顾（含中文搜索方案落地） | P6 |
| P8 | 备份、恢复与导出（**必须真实恢复测试**） | P7 |
| P9 | 同步与冲突处理（20 条契约测试为准入条件） | P8 |
| P10 | 打包、发布验证与交付 | P9 |

**顺序上的两点说明**：
- 保留规格建议的"同步在备份之后"。理由：同步的正确性依赖备份提供的可回退保障；
  若先做同步，协议缺陷会污染数据且无法恢复。
- P0 必须真正执行，不能跳过。当前它是阻塞项。

**交付纪律**（规格 §11 步骤 4）：每个阶段都必须同时具备数据模型 + 界面 + 单元测试 +
集成测试 + 关键错误路径处理 + 迁移覆盖 + 文档更新 + **在目标平台实际运行**。
**不接受**只有界面或用临时内存数据的实现。

| **Q5** | 中文全文搜索方案：接受 trigram 索引的体积代价 / 采用自研 bigram / 降级为子串匹配（明确限制）？ | 不决定就无法交付"支持中文的全文搜索"，而这是 §6.5 的要求。 |
| **Q4** | 本地数据库是否需要加密（SQLCipher / SQLite3MultipleCiphers）？ | 影响 ADR-0002；加密**不能在后期原地加**，需要在阶段 1 前定；同时涉及"忘记口令全库不可读"的取舍。 |

### B. 影响体验与范围（建议在 P1 前回答）

| # | 问题 | 影响 |

| Q3 | 墓碑**永久保留**是否接受？软删除 180 天 / op 日志 90 天压缩 / 孤儿附件 30 天是否合适？ | 数据可恢复性与库体积；墓碑永久是防止"离线设备复活已删数据"的必要条件 |

### C. 我按规格默认值自行决定的事项（如不同意请指出）

规格 §12 给了默认值，以下我按默认值或据技术验证作了决定，均已写入 ADR：

1. **同步方式**：自建 op-log + 字段级版本向量（ADR-0003）——不买现成引擎，
   理由与全部候选方案评估见 ADR-0003 §理由。
2. **本地库**：SQLite 3.53.4（`package:sqlite3` 3.x 打包）+ drift + 手写迁移（ADR-0002）。
3. **删除/归档语义分离**，删除走墓碑；`entity` 墓碑永久保留（ADR-0005，待 Q3 确认）。
4. **附件**：内容寻址（sha256），导入即复制；附件与外部链接**拆成两个实体**（ADR-0004）。
   规格原文把两者合为一个 `Attachment / ExternalReference`，其字段规则与"备份含附件""文件丢失失效"
   等规则只适用于本地文件（⚠GAP-04）。
5. **收集记录的多值与多方关联统一用集合语义**（⚠GAP-03）：
   规格 §4.6/§4.7/§4.10 的规则要求"多个任务/多个引用"，但字段建议只给了单个 `project_id`/`task_id`。
   我按**关系规则**实现（多值用 `relation`/`set_element`），单值列只保留真正的 1:1。
6. **V1 不支持重复提醒**（规格 §4.3 允许不实现）。
7. **文本冲突只保留两版 + 人工处理**，不做三方合并、不做 CRDT（ADR-0003）。
8. **`TimeEntry.source` 移除 `import`**（规格提到但 V1 无任何导入功能，⚠GAP-11）。
9. **统计同时提供"原始时长"与"去重覆盖时长"**（规格给了二者择一，我两个都做，⚠GAP-14）。
10. **备份默认不加密**（与 §8.5"不宣传绝对安全"一致），提供可选口令加密（ADR-0009）。
11. **Windows 通知/后台按"尽力而为"建模**（平台限制，ADR-0006）。

  **不声称已完成**（规格 §10.4）。
